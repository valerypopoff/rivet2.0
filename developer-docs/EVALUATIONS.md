# Evaluations

`@valerypopoff/rivet2-evaluations` is the single evaluation engine for the Rivet app, CLI, and host integrations. It replaces the retired Trivet package. Public user-facing behavior is documented under `packages/docs/docs/evaluations.md` and `packages/docs/docs/user-guide/`; this file owns implementation and host-integration invariants.

## Ownership boundaries

- The active `EvaluationStore` owns the complete instance-local Evaluations domain: suites, datasets, compact baselines, project migration markers, terminal run history, immutable dataset snapshots, recording references, and recording artifacts. None of it is saved into `.rivet-project` or `.rivet-data`. Library recovery validates resources independently: one malformed suite, dataset, or baseline is discarded without hiding unrelated valid resources. Baselines whose suite could not be recovered are also discarded rather than left dangling. Durable validation permits temporarily empty display names while an inline rename is in progress; execution and explicit transfer still enforce the result-affecting contracts.
- Project files remain a one-time legacy import source. On open, Rivet reads a pre-library `attachedData.evaluations` block and legacy `.rivet-data.evaluationDatasets`, validates them, converts datasets to library resources, and then stops writing evaluation data to those files. Legacy IDs were project-scoped, so a collision receives a deterministic project-derived local ID and suite/baseline references are remapped with it. Rivet records each completed source-project migration, preventing repeated opens from duplicating resources or resurrecting a resource the user later deleted. Project save flushes the local library before replacing a legacy file or sidecar. A malformed legacy entry is ignored, so it cannot prevent the project from opening or overwrite a valid local library.
- Storage is selected once during app bootstrap. The desktop app uses `TauriEvaluationStore`, backed by the bundled SQLite database `evaluations.sqlite3` in Tauri's application-local-data directory. A first desktop launch imports every existing evaluation key from the old WebView IndexedDB/local-storage stores into one SQLite transaction, verifies every stored value, and commits the migration marker only with the data. A conflict, native-open failure, or temporarily inaccessible legacy IndexedDB leaves the old source intact, keeps that entire app session on the browser store instead of splitting writes between backends, and retries native adoption on a later launch. The standalone browser uses `LocalEvaluationRunStore` and application-local IndexedDB, with its established local-storage fallback only when IndexedDB cannot be used before the first successful access. Desktop and browser installations are deliberately separate Rivet instances and do not synchronize automatically.
- Hosted wrappers replace the whole store through `ProvidersContext.providers.evaluationStore`. This is one ownership seam rather than separate library and history adapters: a tenant/database-backed implementation receives every definition and evidence operation, and Rivet does not open a local evaluation database when that override is supplied. The adapter must isolate tenant and project ownership, make `putLibrary` and artifact mutations durable/atomic at its own boundary, and implement the inherited run-history methods. A hosted adapter that exposes resource versions should also expose the optional sync-issue subscription, conflict-resolution, and retry capabilities: the app keeps a conflicting local suite/dataset visible until the author explicitly accepts the server version or saves their put as a new copy. Transport and server-transient failures are retryable save states, not edit conflicts. A deprecated run-only `evaluationRunStore` override remains a compatibility bridge, but new wrappers must use `evaluationStore`; Rivet never requires the wrapper to expose that database as an HTTP server.
- In Studio Server, suite and dataset definitions are tenant-wide shared application resources, never project-file resources. A suite references graph and dataset IDs, but does not belong to the project currently open in the editor; run history, snapshots, and recordings remain separately project-scoped. An evaluation-library rename must therefore synchronize and notify through the evaluation boundary, never through workflow-tree or project-content reconciliation.
- At execution start the adapter writes an immutable, project-scoped `EvaluationDatasetSnapshot`, keyed by the stable dataset ID plus canonical fields and cases. Distinct dataset resources therefore cannot alias the same historical snapshot even when their content is identical. The durable boundary rejects missing or mismatched project ownership, invalid creation timestamps, and fingerprints that do not match the canonical dataset content. Stores keep the first value for a valid key, so a later live-dataset edit cannot rewrite historical evidence; cosmetic resource names do not invalidate the snapshot.
- `EvaluationRunStore` owns full runs, observations, content-addressed dataset snapshots, and recording references. Its V2 physical layout stores a small per-project run index, one record per run, one record per dataset snapshot, and one record per replay artifact. Run append, rename, delete, snapshot creation, recording-manifest changes, and library replacement use compare-and-swap batches. IndexedDB performs each batch in one read/write transaction; Tauri performs it in one SQLite transaction. A custom key/value backend gets the same logical operations, but provides strong cross-client atomicity only when it implements `applyBatch`. The old aggregate run and snapshot keys remain read-only migration sources: migration is lazy, restartable, commits the V2 index/artifacts as one batch, and keeps V1 values for rollback rather than deleting the only copy. Run listing still materializes every selected project's full run records; summary pagination and separate trial-detail records require the future repository contract and must not be claimed by a host adapter today.
- Replay artifacts are individual database values referenced by a small per-project manifest, not one repeatedly rewritten project blob and not a fixed-size project cache. Normal successful artifacts therefore remain available for their 24-hour temporary-retention period instead of older trials disappearing as later recordings arrive. The old aggregate recording array migrates in place on first access. A failed migration leaves its source readable and retries on a later access; it never deletes the source before the database transaction commits. Malformed run-history envelopes, snapshot envelopes, recording manifests, and individual recording artifacts fail closed: reads and dependent writes report the storage problem and leave the raw value untouched instead of replacing it with an empty collection. Recording artifacts are validated on writes as well as durable reads. A shell that cannot initialize IndexedDB falls back to legacy storage only before it has successfully used IndexedDB; it never splits a history across backends after that point.
- `runEvaluationSuite` publishes revisioned `run-started`, single `trial-settled`, and `run-finalized` events. The application applies one trial at a time with structural sharing and serializes `applyRunEvent` writes per run. The initial run shell is durably attempted before the first graph starts; each settled trial is checkpointed before that worker takes another item. The legacy `onUpdate` callback remains available for compatibility and pays for detached full snapshots only when requested. Checkpoints make already-settled evidence survive an application failure, but the current product does not yet own a cross-window execution lease, classify abandoned running records as interrupted, or offer resume. A persisted nonterminal record must therefore not be presented as safely resumable.
- The Runs tab merges a delayed history read with the in-memory run by revision, preferring a terminal snapshot on an equal revision without ever replacing a fuller equal-revision trial set with a partial copy. Recording references and warnings may enrich that fuller evidence. A read that began just before the final write must never turn a completed run back into “in progress.” History loading is keyed only to the selected project and suite, never to an evaluation lifecycle transition: the terminal runner event atomically installs and selects the terminal in-memory run before recording retention and final history persistence begin, and the later persistence refresh enriches that same selected entry. A completion therefore cannot briefly render an older selected history entry. Each asynchronous history read carries a generation token, so a suite/project switch or a completed run deletion invalidates an earlier read rather than letting it restore stale history. Deleting a terminal run removes that run and its replay recordings only after confirmation; dataset snapshots and compact baselines remain immutable evidence, including a baseline that was promoted from the deleted run. If run or replay persistence fails, the run UI must show the specific storage failure as a history warning without changing the evaluation's execution or quality result. `EvaluationRun.name` is separately user-owned history metadata: the inline Runs-header rename persists through the run store and later progress/final events preserve it. An absent or blank name renders as **Unnamed**. Suite and dataset names are edited inline from their workspace H1s, so definition and dataset panes never duplicate name fields.

The shared-library conflict dialog has executable presentation-model coverage for server-version acceptance, whether a retained local resource can be copied, deletion conflicts, and retryable transport failures. Do not replace that coverage with source-text assertions: the repository test-style gate rejects new tests that read production source files instead of exercising their behavior.

The runtime-independent application lifecycle lives in `utils/evaluationExecutionLifecycle.ts`. Local and remote hooks provide graph execution, runtime preparation, recording production, UI events, and notifications; the lifecycle service owns dataset snapshotting, runner invocation, ordered run checkpoints, recording-retention finalization, run-name preservation, storage-warning aggregation, and terminal history persistence. Storage failures after graph execution remain evidence warnings rather than changing the execution or quality result. This is the single invariant path for both built-in runtimes. Abort-controller registries and the runtime-specific recording producer still belong to their executor adapters; a future controller/adapter contract must make those concurrency capabilities explicit before adding additional runtimes.

The Evaluations overlay may unmount while Canvas is active, but its session-only suite and Runs presentation survives in `evaluationsState`. A successfully listed history marks an exact `{ projectId, suiteId }` scope as warm; returning to that scope reuses its cached runs, selected run, trial score order, opened trial cards, and scroll position without scheduling another complete-store read solely because the overlay remounted. Opening a dataset is a peer-editor navigation event, so it leaves the last suite's warm history intact. Returning to that suite restores its Definition/Runs/Compare section, selected Definition editor, Additional settings disclosure, selected run, and opened trial cards synchronously. Selecting a different suite replaces the single active history cache and hydrates that cold scope, while suite editor presentation remains keyed by project and suite. Durable history is read only when the selected project/suite scope is cold. A read failure preserves cached or in-memory execution evidence and displays a non-blocking history warning. Progress or terminal snapshots alone never mark a scope warm, because they cannot prove the durable list is complete. Deleting a suite prunes every session presentation, sort, scroll, and active Runs entry keyed to that suite across project scopes, preventing a later resource from inheriting stale UI state; it deliberately leaves durable project run history as immutable evidence. Loading another project clears the applicable active history scope; project reset also clears all Runs and suite-editor presentation preferences. `ProvidersProvider` resolves the fallback evaluation store solely from the explicit `evaluationStore` / legacy `evaluationRunStore` identities, not the wrapper's `ProviderOverrides` object or unrelated adapter identities. A host may therefore rerender with a fresh equivalent overrides object, or replace a path/data-reference/static-data adapter, without reinitializing local evaluation persistence or remounting its cache-owning UI. Replacing either explicit store identity is intentional: it establishes a new durable evaluation boundary and reinitializes the app against that store.

- A graph executor is supplied through `EvaluationGraphRunner`. The engine never assumes Browser, Node, remote, or hosted execution.
- The package stays dependency-light: the portable engine uses Rivet Core for graph contracts and YAML only for project-data serialization; collection and scheduling logic remains local and inspectable.

Do not put raw model output, prompts, credentials, recordings, or complete historical runs in a project file. Baselines in the local library store compact aggregate/per-case metrics and provenance so changing a baseline does not change the executable graph fingerprint. A scoring evaluation can become a baseline only after every requested trial has a usable score; execution benchmarks may still be promoted for performance comparisons because they intentionally do not judge output quality.

### Hosted-store contract

A wrapper passes a stable, tenant-scoped store instance through `RivetAppHost`:

```tsx
<RivetAppHost providers={{ evaluationStore }} />
```

`RivetAppLoader` calls optional `initialize()`, reads `getLibrary()` before mounting the editor, and then serializes detached library snapshots through `putLibrary()` only after an actual edit; hydration itself is not written back. Hydration is tied to the exact evaluation-store and settings-storage provider pair: if a wrapper changes stores (for example, during a tenant switch), the editor unmounts until the new pair is hydrated, any prior shared-library sync issue is cleared, and a superseded asynchronous load cannot publish its library. This prevents the previous tenant's in-memory library or conflict dialog from crossing into the replacement store. Operational code obtains the same object through `useEvaluationRunStore()`, so run history and recordings cannot accidentally fall back to a local browser store. The source host barrel exports both `EvaluationStore` and `useEvaluationStore`; wrappers should not import the app's private provider implementation. Store implementations may use the package-level `normalizeEvaluationLibrary()` helper to apply the same resource-by-resource recovery and de-duplication rules as Rivet's built-in stores. Normalization also removes baselines whose suite is absent; callers must not retain dangling baseline references merely because the rest of a library envelope is structurally valid.

Hosted stores can expose `subscribeLibraryInvalidation` for the authenticated evaluation-library SSE stream. Its `{ epoch, revision }` token represents an external mutation or required resync only: optimistic rebuilds, local acknowledgements, conflict resolution, retries, and ordinary snapshot reads must never emit it. The loader permits one refresh at a time, coalesces newer revisions, and retries a failed or replica-lagged refresh with bounded backoff. It advances its write-observation baseline before installing the rebased library, so remote synchronization cannot write the snapshot back. A visible external resource change receives one non-blocking evaluation-specific toast (including an exact rename when it is the only change); initial hydration, self events, metadata-only changes, and resource conflicts do not. A conflict remains owned by the explicit shared-library resolution dialog.

A hosted implementation should keep the store object stable for the mounted tenant and enforce these rules:

- `getLibrary`/`putLibrary` address one tenant-wide reusable library; run, snapshot, and recording methods additionally enforce the supplied `projectId`.
- `putLibrary`, `put`, `updateRunName`, snapshot writes, retention updates, and deletes are durable before their promises resolve. Concurrent writes for the same logical record must be serialized or use optimistic revision checks.
- Implement `applyRunEvent` idempotently when durable live checkpoints are supported. Repeated or older revisions must not duplicate a trial or replace newer evidence. Omitting it is supported, but means the host retains only the final run and must not advertise interruption recovery.
- Recording payloads can be much larger than run summaries. Store them separately or in blob/object storage while keeping immutable recording IDs and project/run/trial ownership checks.
- `initialize()` may run schema migrations, but it must not return until later reads are safe. Return a recoverable `warning` only when the implementation has deliberately selected one complete fallback for the session.
- Do not inject only `providers.storage` and expect it to own Evaluations. That provider controls Rivet's grouped settings atoms; `providers.evaluationStore` is the explicit database seam.

## Resource transfer

Evaluation datasets use a versioned JSON export for lossless interchange; importing from the **Datasets** sidebar creates a new local-library dataset, while importing from an existing dataset replaces only that resource's fields and cases. JSON transfer validates every declared field type and every supplied case value before serialization or import. CSV remains a case-row format and therefore requires the destination dataset's field contract to already exist; its parser rejects duplicate or empty case IDs, invalid row widths, unsupported boolean/tag encodings, and typed cell values that do not match that contract instead of deferring the failure until execution.

An evaluation-suite export is a versioned JSON bundle containing exactly one suite and the dataset named by that suite's `datasetId`. Import creates fresh suite and dataset IDs in the local library, retains field and case IDs so suite bindings and expected-value references remain connected, and never overwrites an existing resource. Target and evaluator graph IDs remain references: a bundle does not copy graphs, so a currently open project that does not contain those IDs shows the normal repairable missing-graph state. Bundles intentionally exclude baselines, run history, recordings, and dataset snapshots because those artifacts are project/run-store evidence rather than reusable suite configuration. The CLI cannot read Rivet's application-local library; use this bundle with `rivet evaluations run --project <project> --suite-file <bundle>`.

Legacy project attachment deserialization is a trust boundary. It validates the nested suite and baseline structure before returning typed data, then normalizes legacy baseline accounting and quality metadata. Malformed array entries or missing structural fields must fail with a path-specific error rather than reaching editor or comparison code as a falsely typed value.

## Runner contract

`runEvaluationSuite()` accepts application-local datasets for any currently open project and rejects only a legacy dataset that explicitly belongs to a different project. It validates graph-input bindings before any work starts. Every required Graph Input must have a bound input-role dataset field or a static graph default. Every supplied value in every enabled case, including unbound metadata, must be portable JSON and compatible with its dataset field's declared type; no `inferType` fallback is allowed. The workspace derives the same type issues for both Run actions, while the package runner remains authoritative against stale or programmatic invocations.

The runner uses a bounded worker pool (default 4, maximum 32). Ordering remains case order then trial number even when work finishes in another order. It passes an `AbortSignal` to queued and active target/evaluator work and preserves completed trials after cancellation. Graph and LLM retry policies remain the only retry behavior.

New integrations should consume `onEvent`, whose event size is proportional to newly settled work until the one terminal reporting shape is published. `run-started` contains an empty detached run shell and is awaited before graph work begins. `trial-settled` contains one detached trial, a monotonic revision, the stable run/project/suite identity, requested/settled counts, and no accumulated prior-trial payload. `run-finalized` contains the complete terminal `EvaluationRun` once for existing reporters and comparison code. Event handlers may be asynchronous; the worker that settled the trial waits for its handler, allowing an application repository to apply backpressure and establish ordered durability. `onUpdate` is deprecated compatibility behavior and intentionally clones the complete accumulated run after each trial only when a caller supplies it.

Every run explicitly declares its purpose:

- `evaluation` runs the suite's selected evaluation mode. Legacy suites without `evaluationMode` are pass/fail and require at least one required assertion, required evaluator graph, or threshold. A `scoring` suite requires at least one evaluator graph that returns a score. The runner rejects a definition that could not judge output quality before it starts any target graph. Required dataset values remain mandatory in both modes; values used only by preserved pass/fail assertions are not revalidated while scoring.
- `execution-benchmark` measures execution, latency, usage, cost, tools, and outputs without assigning a quality pass or failure. It is the explicit way to inspect a graph with no quality criteria.

Run and trial records keep execution and quality independent. `executionStatus` says whether work completed, errored, or was canceled. Pass/fail `qualityStatus` is `passed`, `failed`, `not-evaluated`, or `unable-to-evaluate`; a complete scoring run is `scored`. A target graph error is **Error / Failed** in a pass/fail evaluation because the target did not satisfy the suite; the same execution is **Error / Not evaluated** in an execution benchmark because no quality judgment was requested. In scoring mode any target, evaluator, or missing-score failure leaves available averages inspectable but makes the run **Unable to evaluate / scores incomplete**; it must never become a false complete score.

Execution timing is stored as milliseconds in `EvaluationExecutionMetrics` and in latency threshold metrics for compatibility, but the Evaluations UI accepts latency threshold values and presents all run, trial, and comparison timings in seconds. The Runs summary begins with Quality, Execution, and Total cost. Quality combines its status and applicable coverage on one result line beneath the label. A running suite stores its planned target-execution count on the run itself, so Quality can show **Evaluating: ran/total ran** without depending on a later suite edit; the not-yet-authoritative cost, score, and latency facts consistently show **…**. In scoring mode, Score and **Target graph latency** are side-by-side half-width factoids, each containing mean, median, and P95 values; pass/fail runs show a full-width Target graph latency factoid. Each factoid uses the subtle warning surface only for an authoritative issue: failed or unable quality, errored/canceled execution, partial or unavailable completed cost, incomplete/unavailable scoring evidence, or incomplete/invalid latency evidence. An intentional execution benchmark and an in-progress run stay neutral. Incomplete accounting is shown beside Total cost only when provider pricing is missing. Latency statistics use every incurred trial; score statistics use equal-weight per-case mean scores so **Mean score** preserves the suite's overall-score semantics. Median averages the two middle values for an even sample; P95 uses nearest rank, so it is the maximum when fewer than 20 samples exist. The scoring-only **Sort by score** control appears directly before the trial rows, after the **Scores by case** summary, with the explicit choices **Score: highest first** and **Score: lowest first**. It must derive a new ordered view of immutable run or trial records, keep unscored entries last, and never rewrite execution order in storage. Its view preference, opened trial cards, and scroll position belong to the project-and-suite-scoped Evaluations session state rather than the conditionally rendered Runs panel, so they survive switching away from and back to that tab or workspace.

Run-store normalization treats scoring evidence as authoritative: a completed trial is `scored` only when every evaluator observation contains a valid normalized score, and a completed scoring run or baseline is `scored` only when every requested trial has that evidence. Stored status labels cannot upgrade incomplete evidence to a complete score. The final runner update may add aggregate facts, but it must preserve every already-published settled trial exactly. Local and remote executor state handoffs additionally accept only monotonic run revisions, so a delayed running update cannot overwrite terminal trial score or duration values on screen.

The target graph has already executed exactly once when an evaluator starts. Evaluators judge that result; they must not invoke the target again. Each evaluator Graph Input has an explicit source binding to one target Graph Output, one evaluation-dataset field, or one evaluation-context object. Dataset-field bindings are not restricted by field role, so reference data and evaluator metadata can feed ordinary evaluator inputs directly. Target-output and dataset-field sources must be compatible with the evaluator Graph Input's declared Rivet type, and every enabled case must contain each bound dataset value. For a story/glossary suite, bind the dataset `story` field to the target graph, then bind the evaluator's `candidateGlossary` input to the target glossary output and its `referenceGlossary` input to the dataset reference field. No adapter graph or name convention is required.

The optional context sources are `case`, `inputs`, `expected`, `outputs`, and `run`. `inputs` is keyed by target Graph Input ID, `expected` is keyed by deterministic-reference dataset field ID, and `outputs` is keyed by target Graph Output ID. `case` is a portable snapshot with the case `id`, `name`, `enabled` state, optional `tags`/`note`, and all `values`; `run` contains trial metadata. Context sources are object values and can bind only to `object` or `any` inputs. Suites created before direct bindings remain compatible: when an evaluator has no `inputBindings` property and declares all five reserved Graph Inputs, the runner supplies the complete legacy context envelope automatically. An explicit empty `inputBindings` array opts into direct mapping and does not activate that fallback.

Every evaluator still declares exactly one Graph Output named `result`, typed as `object` or `any`. In pass/fail mode, `result` requires boolean `passed` and accepts optional `score`, `message`, portable `evidence`, and finite numeric `metrics`. In scoring mode, `result.score` is required. The graph-facing score contract uses the same finite `0` through `100` scale as the UI (`85` means `85/100`); the runner divides it by 100 at the adapter boundary and stores normalized observations so aggregation, thresholds, baselines, and existing run records retain their `0..1` representation. This does not change the built-in Autoeval node's provider-level `0..1` output: an evaluator graph that exposes that value as `result.score` must convert it to the 100-point graph contract. `passed` is optional and ignored in scoring mode. A suite threshold addresses one of those metrics as `custom:<metric name>`; the UI keeps the metric name separate so the persisted contract remains explicit.

## Metrics, provenance, and retention

Execution adapters derive model/tool counts, token usage, known/unknown cost, and timing from physical process events. They do not depend on special Graph Outputs. Adapter results are an untrusted runtime boundary even when their TypeScript signature is correct: successful target and evaluator calls must return non-negative finite duration/cost, non-negative safe-integer counters, boolean unknown-cost state, and portable detached diagnostics. Invalid successful telemetry turns that graph attempt into an execution error so it cannot inject `NaN`, negative counts, or mutable values into aggregates/history. If a graph has already failed, invalid optional diagnostics are discarded without replacing the real graph error. A completed trial with no priced operation is a known zero-cost trial and participates as zero in total and average cost. Unknown provider pricing makes `accountingStatus` partial, but it does **not** change an otherwise valid quality result. It makes quality unable to evaluate only when a configured cost threshold needs the missing value. Every run records suite, dataset, target/evaluator, and execution-mode provenance. Target/evaluator provenance follows static Subgraph, Loop, Cron, and Delegate Tool Call handler references so changing a handler graph makes a baseline stale. It also includes runtime-relevant project configuration: plugins, node prefabs, project data, project references, MCP configuration, and Knowledge Store definitions. Project titles/descriptions, graph/node descriptions, canvas geometry, connection bend points, and UI graphs are deliberately excluded because they cannot change execution; graph names remain material because tool delegation can resolve them. Live project objects may retain optional fields as own `undefined` properties; provenance canonicalizes them using ordinary JSON omission semantics before fingerprinting, while dataset values, evaluator values, outputs, and evidence retain the strict portable-JSON contract. Portable values reject sparse arrays, hidden/extra properties, symbols, and accessors instead of accepting data that would silently change across persistence or adapter boundaries. Fully dynamic graph references remain represented by their owning graph configuration because their eventual target is not knowable before a trial runs. The editor's Browser and hosted/remote adapters persist privacy-bounded provider/profile-attempt provenance with each target or evaluator observation; the Node and CLI adapters expose the same data to their caller and reporters, while their host decides whether to attach an `EvaluationRunStore`.

Every target and evaluator invocation also carries `evaluationRunId`, `suiteId`, `caseId`, `trialIndex`, and a `target`/`evaluator` phase through `GraphExecutionMetadata`. This is host-owned execution metadata, not a Graph Input: it reaches local, Node/CLI, remote-executor event streams, Run Activity, and recordings without changing the graph contract. Browser evaluations route their concurrent process events directly to Run Activity without routing them through the single-run canvas lifecycle, so one completed trial cannot clear another trial's activity.

Hosts decide recording storage. The product policy is to retain failed and baseline recordings, temporarily retain successful candidate recordings for promotion, and always keep compact observations/metrics. Final retention is applied per target or evaluator artifact rather than per trial: a failed evaluator recording remains retained even when the target recording from the same trial is only a temporary successful candidate. Duplicate artifact writes preserve the existing retention decision, so a delayed retry cannot demote a failure, baseline, or manual-retention pin; explicit retention updates own those transitions, and a recording ID is immutable to its original run/trial scope. `EvaluationRunStore` implementations must enforce project/tenant isolation and delete all project-owned runs, dataset snapshots, and recording references with the project. The standalone browser store relies on IndexedDB quota and explicit retention expiry rather than silently evicting artifacts behind still-visible run references. If the platform cannot persist an artifact, the compact run remains valid and receives an explicit count of replay recordings that could not be retained.

Snapshot persistence is intentionally non-blocking for a target run: an unavailable browser quota or host store does not prevent an evaluation from measuring the graph. The final `EvaluationRun.warnings` must state that the exact historical cases were not retained, so replay and comparison UI never imply that the missing snapshot is available.

Dataset snapshots follow retained run history and currently have no independent age cap. A snapshot is persisted immediately before the runner's first asynchronous run write, so a store cannot safely infer that a snapshot is orphaned merely because no run currently references its fingerprint; concurrent cleanup could delete the cases for a run that is starting. Project-wide deletion is the safe host ownership boundary and must remove every snapshot. The standalone browser cannot observe a project file deleted outside Rivet, so local snapshots may remain until browser-origin data is cleared. Hosted stores likewise still need an explicit evaluation run-age/per-suite/total-byte policy and an atomic run/snapshot lease before ordinary summaries, failure artifacts, and snapshots can be reclaimed without evicting baseline/manual-retention evidence. Do not silently reuse an endpoint-keyed recording limit as a suite limit.

Graph evaluator scores are combined as a weighted mean after the graph-facing 100-point value is normalized at the runner boundary. A missing `scoreWeight` means `1`; configured weights must be finite and greater than zero. A weight of `2` gives that evaluator twice the influence of an evaluator weighted `1`, while changing the weight of the only evaluator has no effect. The applied weight is copied to each stored observation, and baseline provenance prevents a comparison from silently treating a changed weighting configuration as compatible. In scoring mode, Rivet first combines evaluator scores within one trial, then averages the requested N trials for each enabled case, and finally gives every case average equal weight in the internally normalized `0..1` score. The UI renders that as `85/100`. `scoredTrialCount` and `missingScoreTrialCount` are stored both overall and per case; an incomplete run still shows available scores and coverage, but never claims a complete result. Switching between suite modes preserves pass/fail assertions and thresholds without executing them in scoring mode, so switching back restores their previous behavior. Dormant pass/fail controls and evaluator labels do not stale a scoring baseline; the mode-relevant evaluator graph, input bindings, and weight still do. Binding order is normalized before fingerprinting, so reordering equivalent mappings does not stale a baseline. Custom evaluator metrics are averaged both globally and per case, preserving the evidence required by compact baseline comparisons. The runner clones portable inputs, evaluator case envelopes, outputs, evidence, and metrics across adapter boundaries, so concurrent Code/evaluator graphs cannot mutate a live dataset or another trial's evidence.

## Editor and integrations

The app state is `state/evaluations.ts`; it composes a persistent local `EvaluationLibrary` with transient navigation/run state. The workspace renderer is rooted in `components/evaluations/Evaluations.tsx`. File providers expose `EvaluationProjectFileData` only as a legacy load/import envelope and never serialize it on save. Existing `attachedData.trivet` is intentionally ignored and omitted from the next save.

Evaluations is a globally available local-library workspace. Its tab stays visible without a project so suites and datasets can be inspected, imported, exported, edited, or deleted. Graph options must nevertheless be derived from an actually opened project tab, never from `projectState` alone: Rivet intentionally keeps a placeholder project in that atom while the Welcome screen is visible. With no project, graph references are shown as unresolved and execution is disabled; Data Studio remains project-scoped.

Live evaluation runs are scoped to the active project. Switching to a different project cancels its evaluation from the first asynchronous setup step (dataset retention and remote preparation included), and every late progress or completion update is fenced by project ID so it cannot populate the newly active project's workspace. Already persisted history remains owned by the original project and is available when that project is reopened.

An unsaved Prompt Designer candidate is additionally scoped to the exact source
project ID and graph ID. It can never be substituted into an Evaluation merely
because a different project happens to have a graph with the same ID.

The workspace resolves every suite's dataset by the local-library `datasetId`. It enables execution only when an active project contains the target and all evaluator graphs; legacy datasets that still carry another project's ID remain a repairable missing reference instead of becoming a late execution failure.

The editor hierarchy is workspace → resource → section; an open project supplies graph resolution and run context:

- `EvaluationSuiteSidebar.tsx` owns explicit suite and dataset selection. It shares Canvas's persisted sidebar width, resize handle, panel palette, and active-row treatment so workspace navigation stays consistent.
- `suiteTransfer.ts` owns the versioned suite-plus-dataset bundle format. Validate the source before assigning destination IDs; the dependency relationship must be checked before a suite is retargeted to its newly imported dataset.
- `EvaluationSectionTabs.tsx` owns the horizontal Definition, Runs, and Compare tab strip. It is rendered only for an explicitly selected suite; a directly selected dataset opens its own editor rather than becoming a suite tab.
- `EvaluationDefinitionTabs.tsx` owns the counted editor tabs shown below Check type. Pass/fail exposes Deterministic checks, Custom evaluator graphs, and Thresholds; scoring exposes only Custom evaluator graphs. The selected editor is the only mounted tab panel, and mode changes derive a valid active tab immediately without deleting the hidden pass/fail configuration.
- `EvaluationSuiteRunStatus.tsx` owns the suite-wide execution and status surface. It stays pinned to the top-right of the Evaluations scroll viewport and presents every suite-level blocker or caution in one persistent warning list on Definition, Runs, and Compare. Its zero-height sticky wrapper establishes its own formatting context, so the surface's top margin cannot shift the suite header below it; suite and dataset title headers therefore use the same top inset. On wide layouts, the normal header keeps **Export suite + dataset** directly to the left of the floating run block; the block itself is left-aligned and contains **Run evaluation**, optional **Run execution benchmark**, then the target-execution count. Its `clamp(350px, 20vw, 520px)` width makes the block smaller while retaining room for the common action layout; its wrapping layout moves the execution count to a subsequent line before it splits the run actions when space is constrained. Only at widths of 1260 px or below does the status surface switch to the full-width narrow toolbar and include export in that same action row, so export never becomes detached below the suite title. Warning derivation is mode-aware: scoring never cites pass/fail-only thresholds or expected-value checks. Field- and card-specific authoring diagnostics remain beside the controls that repair them; do not render duplicate suite-level warning paragraphs lower in a definition tab.
- `CreateEvaluationSuiteModal.tsx` creates a suite atomically after the author explicitly chooses a name, target graph, and existing/new dataset. The editor must not silently use the first graph or dataset.
- `EvaluationFormField.tsx` owns the label, control, and help-text spacing used by Evaluation dialogs and definition editors. By default it renders label, control, then help text; a field can explicitly put its help text directly after the label when the hint needs to explain the control before the user reaches it. The **Dataset and target** section owns dataset selection first, followed by target-graph selection and dataset-to-target input bindings. Check type follows the complete target block because it controls which quality/scoring editor appears after it. Repeated assertions, evaluator graphs, and thresholds use labeled editor cards rather than anonymous wrapping control rows. Authoring tables (dataset fields and graph-input bindings) use compact columns, vertically centered one-line input names where space permits, wide value-source controls, and exactly one divider below the column headings; they override the shared table body's bottom border and do not draw dividers between or after data rows. Evaluator and deterministic-check names are inline-editable card titles, their required switches remain beside or below the title as appropriate, and every editor card places its remove affordance in the top-right corner. The Required switch is available only in pass/fail mode; scoring requires every evaluator result and therefore does not render a non-actionable switch. The evaluator-graph contract diagnostic belongs directly below the graph picker. Deterministic expected-field diagnostics belong directly after their dataset-field picker; other assertion diagnostics remain beside the controls that repair them. Binding and score-weight diagnostics remain next to their respective controls. Threshold controls and human-readable run results present rates, normalized scores, and maximum regressions as percentages, while persisted suite values remain normalized `0..1` for engine, CLI, and legacy-bundle compatibility. Value-source menus group target outputs, dataset fields, and evaluation-context envelopes with labelled separators. Dataset transfer actions live in the screen header's top-right, the dataset summary is an informational block, and the header's clickable usage count reveals dependent suites on demand. Evaluation datasets deliberately have no description metadata; legacy descriptions are discarded during normalization and transfer. Run actions use the shared green active treatment, while disabled run actions replace the green fill with the neutral disabled surface, muted text, reduced opacity, and a not-allowed cursor so the entire control reads as unavailable. The target-execution count is rendered once below the run-action row rather than repeated in every run button. Execution settings keep trials and concurrency visible, retain their explanatory paragraphs with deliberate spacing, and reveal timeout, recording retention, and seed controls only after **Additional settings** is expanded; a validation issue automatically reveals those controls. That closed control uses the same hover treatment as suite export. When expanded, it is replaced by a compact titled panel with an icon-only close action; controls are single-column, have deliberately spaced rows, put field hints directly below labels, and the panel has no active-color edge. Sidebar resource context menus use a fixed-width, single-line destructive action with clear error-tinted hover and focus states.
- `EvaluationSelect.tsx` owns Evaluation dropdown placement. It renders menus through Rivet's top-level portal with fixed positioning so workspace and modal scroll regions cannot clip them.
- `EvaluationConfirmModal.tsx` owns confirmations for reference-clearing changes and unusually large runs. Evaluation workflows must not fall back to browser-native confirmation dialogs, whose layout and theme differ across hosts.
- `evaluationWorkspaceModel.ts` contains pure selection, reference-status, comparison-availability, and authoring-preflight derivation. Before a run is enabled, the editor checks bindings and enabled-case input values, deterministic-check output/operator/expected-value compatibility, evaluator graph contracts, threshold context, and worker/seed settings. The package runner remains authoritative and repeats the complete validation before allocating workers. Large-run confirmation uses the selected purpose: a quality evaluation includes evaluator-graph executions, while an execution benchmark counts only target executions because it never invokes evaluators.

The active resource and project-and-suite-scoped editor presentation are transient workspace state in `state/evaluations.ts`, not library or project data. Every new workspace state starts with an empty `suitePresentationByScope` map, so no suite can inherit another suite's open tab or disclosure state. They survive leaving Evaluations for the graph editor, opening a dataset briefly, or visiting another workspace. Project changes always clear in-flight run/navigation state and presentation caches. Legacy selection metadata is discarded while deserializing the old project envelope, so an older host or in-memory object cannot affect the local library. Opening a retained recording closes the Evaluations overlay and shows recording mode only around the graph canvas; the recording border must not leak over Evaluations or other project workspaces.

Changing a suite's dataset or target graph is a resource-boundary edit. Dataset reassignment clears target bindings, evaluator bindings sourced from dataset fields, and deterministic-check field references while preserving target-output and context evaluator bindings. Target-graph reassignment clears target bindings, deterministic-check output selections, and evaluator bindings sourced from target outputs while preserving dataset and context bindings. The confirmation copy must name every affected binding layer; stale cross-resource bindings must not survive silently. Declared target-output types are validated before execution, and a direct target-output binding also validates the actual runtime value before it enters an evaluator graph, so a malformed target result cannot masquerade as a valid score.

Deleting a shared dataset field is also a resource-boundary edit. The dataset editor confirms the operation when any suite uses that field, then removes the field values and clears every target-input binding, deterministic-check reference, and direct evaluator dataset-field binding that names it. It is unavailable while an affected suite is running. Historical runs and baselines remain immutable evidence; the changed dataset fingerprint makes prior baselines stale rather than rewriting history.

Evaluation modals follow the same `AppModalHeader` / `ModalBody` / `ModalFooter` structure as the rest of Rivet. Modal introductions, forms, form fields, field help, and previews are separate vertical groups; reset their native margins and use explicit layout gaps rather than browser or global element margins. The recorded-input dialog also disables its action until a recorded Graph Input execution and a suite with an active-project dataset are available.

Dataset case cells are type-aware authoring controls. String fields accept ordinary unquoted text and persist it on change; booleans use an explicit selector. Numbers, objects, arrays, and `any` values use JSON syntax, with type-specific examples for structured fields; object, array, and `any` case cells use a wide multiline JSON editor rather than a one-line input. Structured editors start at three rows, scroll long values instead of growing with their content, and allow deliberate vertical resizing. Each case is one full-width grid row containing Enabled, Case, Tags, Notes, every typed value, and an icon-only Remove action. Fractional tracks give structured values twice the horizontal share of compact values while zero-minimum tracks keep the row within the workspace instead of creating a horizontal scrollbar. The fixed icon-action track keeps every header exactly aligned with its control column; typed headers render as `fieldName (type)` on one line. Case inputs align to the top edge; the switch and action align to the vertical center of the first control row rather than to a tall structured field. The Fields and Cases editors omit separators between item rows. As with the other authoring tables, Cases draws its single separator below the column labels, never above them or after the data rows. Secondary Evaluations actions use the clearly visible `--grey-darkish` hover surface, and primary add actions use a `+ Add …` label. The editor and runner share `isEvaluationValueCompatibleWithDataType()` so they cannot disagree about a saved value. An invalid structured draft remains visibly marked and disables the suite's Run action until it is fixed; it must never look like a value that was saved successfully. Dataset names are inline-editable headers; datasets intentionally have no separate description metadata. Boolean controls use Rivet's shared switch. Remove actions use the Web app builder's trash icon, with an accessible label, native tooltip, and the sidebar Import hover background.

Evaluation suites and evaluation datasets are peer **application-local** resources (tenant-wide when the app uses a hosted evaluation store). A suite's `datasetId` is an explicit reference to one dataset; any number of suites may reference that same dataset. IDs are globally unique inside Rivet's local evaluation library, so selection and mutation match by resource ID rather than a project ID. The Evaluations sidebar therefore has independent **Evaluation suites** and **Datasets** lists. `selectedSuiteId` and `selectedDatasetId` identify the active resource rather than implying ownership: selecting a dataset opens its reusable case editor and lists every suite that uses it, while selecting a suite opens its Definition, Runs, and Compare sections. Editing a shared dataset affects every suite that references it. Data Studio manages a separate mutable graph-dataset model and does not list or edit evaluation datasets.

Right-clicking a suite or dataset resource row opens its destructive context action. Deleting a suite removes its local-library definition and baselines. A dataset deletion must not leave a required `suite.datasetId` dangling: when the dataset is shared, confirmation explicitly cascades to every dependent suite and baseline. Run history and recordings remain project-scoped evidence, so deleting a reusable resource does not attempt to erase history in projects that may not be open. Deletion is unavailable while an affected suite is running. Dataset snapshots are content-addressed evidence and are intentionally retained by the store's normal lifecycle because they may be shared by historical runs.

The Runs section is an evidence browser, not only an aggregate table. It exposes every trial's resolved Graph Inputs, target outputs, deterministic-check reference values, checks, metrics, provider-attempt diagnostics, errors, and retained recordings. The selected run has an inline editable header backed by `EvaluationRun.name`, and the selector begins with that name or **Unnamed**. Target and evaluator replay actions name the artifact explicitly: **Load target graph recording** or **Load '<evaluator name>' graph recording**. The quality explanation is structurally separated from the summary-card grid so its vertical spacing does not depend on collapsible paragraph margins, spans that grid's full width, and uses the neutral foreground-tinted surface for ordinary states such as an in-progress run. Only a failed/unable quality result or incomplete execution uses the yellow warning surface. Collapsed trial cards use fixed CSS-grid tracks for the case/trial, execution state, quality result, and total evaluation duration, aligning these facts without an HTML table; their toggle label must flex to the available button width so every row resolves the same tracks. Long facts truncate instead of pushing into another column, with the full value available as a tooltip. A completed execution is labeled **Executed**. Trial panels begin collapsed and open only on the user's explicit action; changing the selected history run clears the previous run's expanded cards. Store boundaries normalize persisted records before typed `EvaluationRun` snapshots reach this view; the Runs renderer must not deep-normalize or clone a selected run as part of rendering. The compact list must not serialize inputs, outputs, expected values, evidence, diagnostics, or provider attempts until the user opens that specific trial; the expanded detail retains all existing evidence, replay actions, and search-compatible `<pre>` text. Time is stored in milliseconds but displayed as seconds; non-finite, negative, zero-trial, or missing terminal legacy latency summaries are rendered as unavailable rather than a misleading duration.

For initial Runs rendering, the lightweight summary derivation is memoized by immutable `EvaluationRun` snapshot identity, so returning to the tab does not repeat its observation walk for the same retained run. It still derives newer factoids when a legacy persisted aggregate predates them. All evaluation presentation views, including Compare, trust `EvaluationRun` and baseline records only after the store/runner/library normalization boundaries; a view must not deep-normalize retained history during rendering. Compare filters and labels immutable run references only, while trial details remain lazy.

While a suite is running, its own row in the Evaluations sidebar shows the immediate running indicator. The main workspace tab remains a navigation control rather than a global activity indicator; the application-wide running state is still retained to protect graph execution while an evaluation owns the runner.

The serialized `expected` dataset-field role is presented as **Deterministic check reference**. It is reference data, not an implicit assertion. A deterministic check selects a target graph output and compares it with a literal or reference field, or an evaluator graph interprets the `expected` object. Merely naming a reference field like an output never compares them automatically. Unused reference fields remain visible with an explicit create-check action; the editor may suggest an output only when the match is unambiguous. **Graph input** fields bind dataset values to target Graph Inputs; **Evaluator metadata** travels only to evaluator graphs. Editor preflight also rejects deterministic comparisons whose known output and reference-field types cannot meaningfully compare, instead of allowing an impossible equality check or a trivially passing inequality check to reach execution. Custom output paths are checked with the package's canonical JSON-path parser, so authoring accepts exactly the root, identifier-property, quoted-property, and numeric-index selectors that execution understands.

Quality-check configuration fails closed. A missing output path cannot satisfy `not-equals`, and JSON paths traverse only own JSON properties rather than inherited prototype values. Operators reject malformed expected values as configuration errors instead of presenting them as ordinary quality failures. The deterministic JSON Schema operator supports `type` (including `integer`), `enum`, `const`, string length/pattern, numeric minimum/maximum, array length/items, object required/properties, and boolean `additionalProperties`; malformed shapes and every unsupported keyword are rejected explicitly so an ignored constraint can never create a false pass. Evaluation dataset compatibility likewise accepts only defined portable JSON representations and rejects unknown, function, binary/media, or other non-portable Rivet data types until an exact portable contract exists.

Assertion output-path authoring must call the package-exported `isEvaluationOutputPathSyntaxValid()` helper. It shares the runtime parser for root `$`, identifier property segments, quoted bracket keys, and numeric array indexes; app code must not maintain a second JSON-path grammar that can drift from execution.

Normalized quality reasons are constrained by purpose, execution status, and quality status. For example, a benchmark can never retain a legacy `checks-passed` reason after its quality is normalized to **Not evaluated**, and a canceled run can never retain a pass/fail explanation. Incompatible stored reasons are replaced with the canonical explanation for the normalized state.

The UI must never label successful execution as passed quality. A normal evaluation without an effective quality criterion is invalid and cannot start. An explicit benchmark shows **Not evaluated** for quality while still presenting inputs, outputs, latency, accounting, and recordings. **Unable to evaluate** is reserved for a configured required criterion that could not produce trustworthy evidence, and its exact `qualityReason.message` must be visible.

Missing target graphs and datasets are preserved as broken references. Definition provides selectors to repair them, while Dataset and Run actions stay unavailable. Loading run history is also suite-scoped: no run-store request occurs without an explicit suite, the app filters returned records to the requested suite as a final host-store boundary, and delayed responses from a previously selected suite must be ignored. The Compare view chooses only a completed run with aggregate metrics; failed or canceled history cannot make a valid comparison surface appear blank.

The editor also detects missing evaluator graphs before it starts a suite. It disables Run evaluation and identifies the missing evaluator in the suite subtitle and Definition row. Evaluator contract preflight requires one `result` Graph Output typed as `object` or `any`, validates every direct evaluator-input source and its type, rejects duplicate or stale bindings, and requires every otherwise-unbound Graph Input to have a static graph default. The package runner repeats these checks before allocating workers and validates actual enabled-case values. The five reserved object inputs are accepted only through the documented legacy-envelope fallback; they are not required for newly authored evaluator graphs.

The CLI command is:

```text
rivet evaluations run --project <file> --suite-file <exported-suite-bundle>
```

The CLI cannot read Rivet's local library, so it runs an exported suite bundle. `--suite <id-or-name>` remains available only for a legacy project attachment. The command defaults to quality evaluation and therefore rejects suites with no effective criteria. Its text output renders scoring results as `85/100` plus score coverage. `--benchmark` explicitly runs the same cases for execution measurement with quality reported as **Not evaluated**. A normal completed run that is still **Not evaluated**, or a scoring run that is **Unable to evaluate** because score coverage is incomplete, is a configuration/infrastructure outcome rather than a successful evaluation; a completed benchmark succeeds only when none of its trials errored or were canceled. Normal success, quality failure, and infrastructure/configuration outcomes use distinct exit codes.

Evaluation recording playback resolves the root graph from the recorder's `start` event before loading the artifact into the editor. This matters because evaluator and target artifacts can be opened from the Evaluations overlay while a different graph is on the canvas: replay events are keyed by their authored node IDs, so the editor must switch to the recorded root graph before those outputs can be visible. If the artifact has no root start event or that graph has since been removed, loading fails with a clear error instead of presenting an apparently playable recording with an empty canvas.

JUnit reports completed quality failures as failures, target/evaluator execution problems as errors, and benchmark trials as skipped rather than falsely passed tests. Aggregate threshold failure or unavailable aggregate evidence is emitted as a synthetic `Evaluation aggregate requirements` testcase when no individual trial row represents it. This keeps CI reports consistent with the run-level exit result instead of allowing an all-green testcase list beside a failed aggregate requirement.

Reporter adapters consume normalized `EvaluationRun` v2 records; Gentrace exports completed runs rather than executing a second suite. The Graph Builder harness shares `runEvaluationWorkPool()` for bounded scheduling, cancellation, and stable result ordering, while retaining its intentionally domain-specific fixture materialization, redaction audit, and scoring contracts. It is not a second general-purpose graph-evaluation runner.

## Change checklist

When changing evaluation behavior:

1. Keep the application-local evaluation library, project data, and retained run artifacts separated.
2. Preserve the execution-status versus quality-status distinction.
3. Test binding validation and complete GraphProcessor scheduling, not only node ports.
4. Preserve bounded concurrency, cancellation, deterministic result ordering, and no hidden retries.
5. Add Browser, Node, remote, recording, and hosted-store coverage for new execution semantics.
6. Regenerate the Graph Builder node help if a changed evaluation-facing node contract affects it.
7. Update the workspace overview, getting-started, evaluator-graph, package/CLI, and developer pages when a user-visible contract changes.
