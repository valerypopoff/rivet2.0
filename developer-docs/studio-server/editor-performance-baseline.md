# Local editor performance baseline

## Scope and conclusion (2026-10-25)

Measured source revision: `cdd837a08d320235868682d7e204d7bea0592085`.
This is a post-refactor baseline, **not** a before/after comparison or production
qualification. No application optimization, GCP request, release publication or
deployment was performed. The results justify targeted performance work, not
another broad architectural rewrite.

Follow-up work is specified in the
[editor performance implementation plan](editor-performance-implementation-plan.md).
The plan is pending; the measurements below describe the unchanged baseline.

Two priorities stand out:

1. Keep editor-only dependencies out of dashboard startup. The dashboard requests
   Monaco and a large shared runtime chunk before a project is opened.
2. Reduce repeated work in execution presentation, especially Run Activity
   projection, node-label lookup and immutable journal updates. A real CPU sample
   identifies these paths; project-tab switching and recording playback are not
   the leading bottlenecks in this workload.

## Method and limits

- Windows 11 (`10.0.26200`), Intel Core Ultra 5 245KF, 14 logical CPUs, approximately
  63.5 GiB RAM; Node `22.22.3`, headless Chromium `151.0.7922.34`, 1600×1000 viewport.
- Fresh hosted production build using the repository Vite config, with only an
  isolated output directory, manifest and build-attribution plugin added. The
  production `production/server.mjs` asset handler serves it on loopback port
  5188. This is not a Vite development-server benchmark.
- Synthetic HTTP API responses replace storage, authentication and provider
  services. Ten projects share one explicit bundle identity, contain 999 total
  nodes and form a nine-edge cross-project Subgraph chain. Text nodes are
  deterministic; no model calls or production project contents are involved.
- Browser execution uses the real editor and hosted Subgraph loader over HTTP.
  Remote Debugger uses the real local Node processor and WebSocket debugger.
  The recording is generated by a real Core processor: 1,213 recorded events,
  128,725 serialized bytes. Its replay-project ID is distinct from the saved
  source ID, matching both server recording implementations.
- Cold samples use separate browser contexts. Warm samples reload the same
  context. Playwright request routing is deliberately absent because it disables
  browser caching. External Google Fonts are blocked through CDP, not routing.
- The local production handler serves local assets uncompressed. Reported
  decoded and transferred sizes must not be presented as production wire sizes.
  Gzip figures below are offline estimates, not measured production compression.
- Timings cover Playwright action dispatch and UI readiness/output assertions.
  They are user-visible interaction envelopes, not pure React render durations.
  Three samples are a baseline, not a statistically reliable p95 or an SLO.
- Graphs initially fit to the canvas, where low zoom intentionally hides node
  bodies/outputs. Execution assertions first zoom to a readable level. Tab-switch
  timings use the fitted overview; these are different rendering workloads.
- No API/database latency, mobile hardware, throttled network, provider HA relay,
  native desktop startup or multi-hour memory soak was measured. One final heap
  snapshot cannot establish a memory leak or its absence.

## Final passing sample

| Operation | Samples | Result |
| --- | ---: | --- |
| Cold navigation → dashboard library visible | 3 | Median 600 ms; range 576–611 ms |
| Cached reload → dashboard library visible | 3 | Median 80 ms; range 78–97 ms |
| First project opened from the warmed dashboard | 1 | 568 ms |
| Remaining nine projects opened individually | 9 | Median 171 ms; range 158–304 ms |
| Switch between ten already-open project tabs | 20 | Median 137 ms; range 121–151 ms |
| Browser execution → root output and idle run control | 3 | Median 2,820 ms; range 2,630–3,147 ms |
| Node execution producing debugger events | 3 | Median 111 ms; range 101–155 ms |
| Remote run start → changed root output visible | 3 | 556, 865 and 1,482 ms |
| Play recording → root output and idle playback control | 3 | Median 137 ms; range 135–138 ms |

The Core fixture-generation run took 158 ms. It has no browser presentation or
hosted HTTP access checks; it is **not** an apples-to-apples comparison proving
that the browser engine is a particular multiple slower.

The debugger sequence is a burst: a new run starts after its predecessor's root
output appears, not after every queued UI update has settled. The increasing
output latency indicates backlog under this burst, **not** a demonstrated leak,
steadily degrading connection or production regression. The final dependency tab
reports `Remote run completed.` before disconnecting. A follow-up steady-state
debugger comparison must wait for every run's terminal projection first.

Repeated playback completed successfully, the drawer contained 100 actual
activity rows, and no page exceptions were captured. Rows are a functional
assertion, not a claim that every cross-project event appears in one drawer.

## Measured loading graph

Cold dashboard readiness requested 12 JavaScript resources totaling 12,675,570
decoded bytes (about 12.1 MiB). The offline gzip equivalent is approximately
2.7 MB. Warm reload transferred zero bytes for those JavaScript resources;
its HTML/API requests are not included in that zero. Cold main-frame long tasks
totaled 261–273 ms per sample; warm samples had no observed >50 ms long tasks
before the dashboard readiness checkpoint.

| Requested before opening a project | Decoded bytes | Offline gzip bytes |
| --- | ---: | ---: |
| `useHostedSurfaceDismiss-*.js` shared chunk | 5,835,078 | 1,146,738 |
| `monaco-editor-*.js` | 4,484,979 | 1,001,152 |
| `atlaskit-*.js` | 1,326,892 | 312,387 |
| `DashboardPage-*.js` | 690,750 | 140,962 |

The shared chunk's name is a Rollup naming artifact: **the small dismissal hook
does not own 5.8 MB of behavior**. Module attribution includes Lodash, the AI SDK,
Google GenAI and shared runtime/state modules. Investigate import reachability
and dependency boundaries rather than splitting that hook based on its filename.

Opening the editor additionally needs `HostedEditorApp-*.js` (4,444,459 decoded
bytes / 1,004,432 offline gzip bytes), plus smaller editor/worker resources.
Conversely, the large tokenizer, dictionary and statistics-chart chunks were not
requested at the measured readiness checkpoints. Their build warnings alone do
not justify making them the first optimization target.

## Execution costs and bounded follow-up

A fourth, separately profiled Browser run is excluded from the three ordinary
timings. Chrome's CPU sample identifies:

- Immer copying, proxy writes and finalization in journal/state updates.
- Run Activity invocation-view construction and its resolver's repeated graph,
  node, value and label lookups. `buildRunActivityViewModel` rebuilds/maps/sorts
  the selected root's invocation list.
- `NodeRegistration.#dynamicDisplayNames`: the getter maps the entire registry
  even when `getDynamicDisplayName` requests one label. This had approximately
  182 ms sampled self time in the profiled run. That is a particularly narrow
  candidate for improvement without changing execution semantics.

These are sampling correlations, not a promise that eliminating any one call
will save its entire sampled duration. Profile frames also include unattributed
browser work, garbage collection and React; no single function explains the
complete end-to-end duration.

The API counters recorded 144 `/access` requests across four Browser runs:
36 per run, in addition to nine `/execution` loads per run. Counts grow down the
chain: the deepest target receives eight access checks per run. The owning path
is `GraphProcessor` topology traversal's cached-target revalidation, forwarded
by `hostedSubgraphProjectLoader.validateTarget`. Repeated traversal is a real
amplification opportunity, but authorization must not be removed or cached across
caller/project/version boundaries to improve a benchmark.

Recommended next work, in order:

1. Defer Monaco and editor/provider runtime reachability until those capabilities
   are needed. Re-run cold dashboard and first-editor measurements: moving all
   delay to the first project open is not a complete improvement.
2. Optimize direct node-label lookup and index/memoize Run Activity resolution
   within explicit project-binding/run lifetimes. Consider incremental projection
   or frame-batched publication while retaining every accepted journal event and
   terminal signal. Preserve cancellation, replay and inactive-tab behavior.
3. Review repeated Subgraph topology/access checks with security invariants intact.
   Measure request counts and timing on the same nine-edge chain. Do not silently
   introduce stale authorization or skip validation on cache hits.
4. Recheck steady-state and burst debugger latency after presentation changes.
   Keep tab switching and repeated playback as no-regression controls.

Do not raise performance thresholds, remove safety checks or begin another broad
refactor merely to turn these numbers green. No pre-refactor performance data was
captured, so this report makes no claim of a speedup or slowdown caused by the
completed refactor.

## Local evidence and reproduction

Ignored local evidence lives under `artifacts/benchmarks/editor-20261025/`:

- `results.json`: raw readiness/resource/long-task samples and API counters.
- `summary.json` / `summary.txt`: derived statistics and chunk attribution.
- `execution.cpuprofile`: fourth-run Chrome CPU sample.
- `dist/profile-attribution.json`, `dist/profile-manifest.json`, `build.log`.
- `editor.perf.spec.ts`, `playwright.perf.config.ts`, `vite.profile.config.ts` and
  `analyze.mjs`: diagnostic harness, not new permanent CI lanes.
- `browser.log`, `final.png`, `test-results/`: passing browser evidence.

The harness's local absolute paths, pinned SHA and browser executable must be
adjusted for another machine/revision. Do not reuse its source identity blindly.
Build before running the browser; do not rebuild Core while a Node fixture is
importing its compiled exports. The config is layered on the owning repository
configs rather than replacing asset serving or application execution.

```powershell
$env:RIVET_ENV_FILE = 'F:/Programming/Rivet2.0/artifacts/refactor-qualification/isolated.env'
node .yarn/releases/yarn-4.17.1.cjs workspace @valerypopoff/rivet-studio-server-web exec vite build --config F:/Programming/Rivet2.0/artifacts/benchmarks/editor-20261025/vite.profile.config.ts
$env:PLAYWRIGHT_HEADLESS = '1'
$env:PLAYWRIGHT_SLOW_MO = '0'
$env:PLAYWRIGHT_BASE_URL = 'http://127.0.0.1:5188'
$env:PLAYWRIGHT_EXECUTABLE_PATH = 'C:/Users/valer/AppData/Local/ms-playwright/chromium-1234/chrome-win64/chrome.exe'
node .yarn/releases/yarn-4.17.1.cjs studio-server:ui:observe --config F:/Programming/Rivet2.0/artifacts/benchmarks/editor-20261025/playwright.perf.config.ts
node artifacts/benchmarks/editor-20261025/analyze.mjs
```

The final browser run passed in 28.6 seconds (35.1 seconds including runner
startup). The harness settles its Node processors, terminates its own debugger
clients and closes its own HTTP/WebSocket servers in `finally`. The existing
local application and production resources are not part of this harness.
