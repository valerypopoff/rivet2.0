# createRivetWebAppHandler

## Description

`createRivetWebAppHandler` serves one minimal Rivet web app from a loaded project.

The handler is framework-neutral. It accepts Fetch-style `Request` objects and returns Fetch-style `Response` objects, so wrappers can adapt it to Express, Fastify, custom HTTP servers, or their own VM routing layer.

The handler serves:

- the HTML/client renderer for the selected `Project.uiGraphs` entry
- `GET /app.json` for the selected UI graph definition
- `POST /actions/run` for button actions that run ordinary graphs in the same project

It does not own authentication, routing, domains, tenancy, or deployment. Those stay wrapper-owned.

Markdown components and Markdown-rendered outputs are rendered by the built-in client with the same `marked` Markdown engine and GitHub Markdown CSS baseline used by the Rivet app preview. Raw HTML tokens inside Markdown are escaped for web apps; V1 does not expose arbitrary HTML or JavaScript authoring. The hosted HTML embeds the packaged CSS and browser script, so wrapper servers do not need to mount a separate Markdown asset or provide their own renderer.

## Syntax

```typescript
type RivetWebAppProcessorOptions = Omit<NodeCreateProcessorOptions, 'graph'>;

type RivetWebAppActionContext = {
  request: Request;
  uiGraph: UiGraph;
  component: Extract<UiGraphComponent, { type: 'button' }>;
  componentId: UiComponentId;
  state: Record<string, unknown>;
  actionInput: Record<string, unknown>;
  revisionKey?: string;
};

type RivetWebAppCreateProcessorOptions =
  | RivetWebAppProcessorOptions
  | ((
      context: RivetWebAppActionContext,
    ) => Promise<RivetWebAppProcessorOptions | null | undefined> | RivetWebAppProcessorOptions | null | undefined);

type RivetWebAppHandlerOptions = {
  basePath?: string;
  createProcessorOptions?: RivetWebAppCreateProcessorOptions;
  onActionError?: (context: RivetWebAppActionContext & { error: unknown }) => Promise<void> | void;
  onActionFinish?: (
    context: RivetWebAppActionContext & {
      outputs: Record<string, DataValue>;
      statePatch: Record<string, unknown>;
    },
  ) => Promise<void> | void;
  onActionStart?: (context: RivetWebAppActionContext) => Promise<void> | void;
  resolveContext?: (request: Request) => Promise<Record<string, DataValue>> | Record<string, DataValue>;
  revisionKey?: string;
  uiGraphId?: UiGraphId | string;
};

class RivetWebAppActionHttpError extends Error {
  readonly status: number;
  readonly code?: string;
}

function createRivetWebAppHandler(
  project: Project,
  options?: RivetWebAppHandlerOptions,
): {
  handleRequest(request: Request): Promise<Response>;
};
```

If `uiGraphId` is omitted, Rivet serves the first UI graph in `project.uiGraphs`.

Handler construction validates the project's complete `uiGraphs` collection through core's discriminated UI-graph normalizer. Missing or duplicate legacy component IDs are repaired deterministically without mutating the supplied project. Malformed component types, required fields, action bindings, and enum values throw `UiGraphNormalizationError` with graph and component-index diagnostics before any request is served. Already-valid graphs retain their object identity, so hosts should continue treating a project revision passed to the handler as immutable. The lower-level `renderRivetWebAppHtml(...)` and `runRivetWebAppAction(...)` helpers perform the same validation for the selected UI graph passed directly to them.

`createProcessorOptions` can be a static object or a request-scoped resolver. Rivet always fills in the selected button action graph after resolving those options, so the UI action target cannot be overridden by a wrapper option. If the returned options include `inputs`, those inputs are used. Otherwise Rivet maps the web app state into graph inputs through the button's input bindings. Raw objects become `object` Data Values, homogeneous raw arrays become typed arrays such as `string[]`, `number[]`, `boolean[]`, or `object[]`, and mixed, empty, null-containing, or nested arrays become `any[]`. If the returned options include `context`, that context is used. Otherwise Rivet calls `resolveContext(request)` when provided. If a resolver returns `undefined` or `null`, Rivet treats it like an empty options object and uses the default input/context mapping.

`resolveContext` lets wrappers derive Rivet context values from the incoming HTTP request, for example authenticated user IDs or request headers.

`revisionKey` is an opaque host-owned consistency token. Rivet embeds it in the served HTML and the browser sends it back with action requests. If a handler was configured with a `revisionKey` and an action request sends a different key, the handler returns `409` with `{ "error": "Rivet web app revision mismatch.", "code": "revision_mismatch" }`. The embedded client shows a blocking reload dialog for that code so users explicitly refresh before running actions against the updated app. Rivet does not use revision keys as authentication.

The action lifecycle hooks are for observability only. Use wrapper route middleware for auth, endpoint ownership, and final response policy.

Button actions return both raw graph `outputs` and a `statePatch` for the client renderer. New UI graph actions can define several `inputMappings` and several output bindings in `outputs`. Each input mapping sends one web-app data key to one Graph Input ID. Each output binding saves either the whole output map, when its `outputKey` is empty, or the unwrapped Rivet data value from `outputs[outputKey].value` to its configured web-app data key. Legacy single-output `outputKey` / `outputStateKey` actions still work through the same mapper. If the target graph does not return a configured output key, the action endpoint returns an error response.

Before dispatch, `runRivetWebAppAction(...)` runs core's non-mutating binding preflight. A stale Graph Input/Output ID, duplicate input target, duplicate output data-key write, or blank required mapping fails with status `400` and code `invalid_button_bindings`. Hosts can call `validateProjectUiGraphButtonBindings(project)` before publishing to inspect the same diagnostics without running or modifying the project. Omitted mappings remain valid because graph inputs may use defaults and actions may intentionally ignore outputs.

The embedded client sends only the web-app data keys referenced by the clicked button's input mappings. Unrelated form values and previous output state remain in the browser. `runRivetWebAppAction(...)` applies the same projection for lower-level host integrations, so its action hooks and processor-options resolver receive the action-relevant state only.

Action requests are JSON-only. The request body and `state` must be objects; malformed bodies return `400` responses from the Fetch-style handler. The lower-level helper throws `RivetWebAppActionHttpError` for HTTP-shaped action failures such as revision mismatches or malformed action state, so wrappers can preserve `error.status` and optional `error.code` in their own Express responses.

## Example

```typescript
import { createRivetWebAppHandler, loadProjectFromFile } from '@valerypopoff/rivet2-node';

const project = await loadProjectFromFile('./my-project.rivet-project');
const webApp = createRivetWebAppHandler(project, {
  basePath: '/app',
  uiGraphId: 'my-ui-graph',
  resolveContext: (request) => ({
    url: {
      type: 'string',
      value: request.url,
    },
  }),
});

// In a Fetch-compatible server/runtime:
export default {
  fetch(request: Request) {
    return webApp.handleRequest(request);
  },
};
```

## Request-scoped processor options

Use a resolver when a wrapper needs the same per-request dependencies as ordinary workflow endpoints:

```typescript
const webApp = createRivetWebAppHandler(project, {
  basePath: '/apps/story-helper',
  revisionKey: publishedRevisionId,
  uiGraphId: 'story-helper-ui',
  createProcessorOptions: async ({ actionInput, request }) => ({
    codeRunner: new ManagedCodeRunner(runtimeLibrariesRoot),
    datasetProvider,
    projectPath,
    projectReferenceLoader,
    context: {
      headers: {
        type: 'any',
        value: normalizeHeaders(request.headers),
      },
    },
    inputs: {
      input: {
        type: 'any',
        value: actionInput,
      },
    },
  }),
});
```

## Lower-level helpers

Wrappers that already own Express timing, recordings, debug headers, and error envelopes can call the lower-level helpers directly:

```typescript
import { RivetWebAppActionHttpError, renderRivetWebAppHtml, runRivetWebAppAction } from '@valerypopoff/rivet2-node';

app.get('/apps/:endpointName', async (req, res) => {
  const { project, uiGraph, revisionKey } = await resolvePublishedWebApp(req.params.endpointName);
  res.type('html').send(
    renderRivetWebAppHtml(uiGraph, {
      actionPath: `/apps/${req.params.endpointName}/actions/run`,
      revisionKey,
    }),
  );
});

app.post('/apps/:endpointName/actions/run', async (req, res) => {
  const { project, uiGraph, revisionKey } = await resolvePublishedWebApp(req.params.endpointName);
  try {
    const result = await runRivetWebAppAction(project, {
      componentId: req.body.componentId,
      requestRevisionKey: req.body.revisionKey,
      revisionKey,
      state: req.body.state,
      uiGraph,
      createProcessorOptions: async ({ actionInput }) => ({
        inputs: {
          input: {
            type: 'any',
            value: actionInput,
          },
        },
      }),
    });
    res.json(result);
  } catch (error) {
    const status = error instanceof RivetWebAppActionHttpError ? error.status : 500;
    const code = error instanceof RivetWebAppActionHttpError ? error.code : undefined;
    res.status(status).json({
      error: error instanceof Error ? error.message : String(error),
      ...(code ? { code } : {}),
    });
  }
});
```

`runRivetWebAppAction(...)` accepts an optional `request`. If it is omitted, Rivet creates an internal placeholder request. Pass the real request when your processor option resolver or `resolveContext` needs headers, cookies, URL, or other request metadata.
