## Overview

The **Match case** Node routes an `Input` value to one or more case outputs. Each case has an output port, and `Unmatched` runs when no case matches. It is a switch/case-style control-flow node for strings.

By default, **Plain text** cases use exact, case-sensitive string equality. For example, the case `approved` matches `approved`, but not `Approved` or `approved later`. Turn off **Case sensitive** to ignore letter case while retaining exact whole-string matching. Choose **Regular expression** to use the existing JavaScript `RegExp` pattern behavior; the **Case sensitive** switch does not apply in that mode.

Each case supports Rivet interpolation. Write `{{expectedStatus}}` to add an input named `expectedStatus`, or use a path such as `{{response.status}}`. The case is resolved when Match case runs, before it is compared or compiled as a regular expression. You can also use portless runtime roots such as `{{@graphInputs.status}}`, `{{@context.tenant}}`, and `{{@globals.environment}}`. Output names keep the authored template because their resolved values are run-specific. See [Variables](../user-guide/variables.md) for the complete syntax.

**Trigger** controls whether the node triggers every matching output or only the first matching output. It uses **First matching case** by default. **Output value** controls what each active branch emits: boolean `true` by default, the tested string, or a custom value. When Custom is selected, an unlabeled chooser selects one shared input or individual inputs for each branch.

| Match mode | **Plain text** compares the entire `Input` string exactly. **Regular expression** applies each case as a JavaScript regular expression. | Plain text |
| Case sensitive | In **Plain text** mode, compare letter case exactly. Turn it off to match `approved` and `APPROVED` as the same case. This setting is hidden in **Regular expression** mode. | On |

## Examples

### Route exact statuses

Use the default **Plain text** mode when a service returns a finite set of known values.

1. Set cases to `approved`, `rejected`, and `pending`.
2. Connect the status to `Input`.
3. Connect each case output to the work for that status.

The value `approved` triggers only the `approved` output and returns `true` with the default settings. The value `approved later` triggers `Unmatched` and returns `true` there.

### Route a pattern

Select **Regular expression** when you need a pattern. For example, the case `^ERR_[0-9]+$` matches `ERR_42`. Regular-expression cases use JavaScript `RegExp` behavior, including its syntax and errors for invalid patterns.

### Route a dynamic value

1. Add `{{expectedStatus}}` as a case.
2. Connect the expected status value to the new `expectedStatus` input.
3. Connect the value being tested to `Input`.

The resolved `expectedStatus` value is compared at runtime. In Regular expression mode, a case such as `^{{prefix}}_[0-9]+$` resolves first and is then compiled as a JavaScript regular expression.

## Error handling

When `Input` is missing, `null`, or `undefined`, no case is matched and the node triggers `Unmatched`. In **Regular expression** mode, an invalid regular expression reports an execution error.
