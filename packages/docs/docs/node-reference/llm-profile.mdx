## Overview

LLM Profile packages one reusable inference configuration into a typed
`llm-config` value. Connect it to an LLM Chat node whose **Configuration** is
**From profile**. You can also collect several profile values into an ordered
`llm-config[]` array and use that as LLM Chat's fallback chain.

If an LLM Chat is currently configured inline, use its **Export LLM settings to profile node**
action to create and connect this node automatically with the chat's current
provider and inference settings.

The profile contains:

- provider and model
- the resolved API key and its source metadata
- Custom-provider base URL and Completions/Responses API choice
- common generation parameters
- OpenAI Previous Response ID
- provider-specific reasoning and thinking settings
- provider-native capabilities such as OpenAI Web Search and Google Search Grounding
- custom headers and extra provider options

It intentionally does not contain prompts, response schemas, Rivet tools,
tool-continuation settings, output switches, retry settings, or editor caching.
Those remain on each LLM Chat node.

**Output reasoning** also remains on LLM Chat, in its **Outputs** section: it
controls whether that individual Chat exposes a `Reasoning` output. A Custom
provider profile has no built-in provider-specific reasoning fields, so it does
not show an empty **Reasoning** section.

## Inputs

Settings with **Use input port** enabled appear as inputs. Depending on the
configuration these can include Model, API Key, Provider base URL, generation
parameters, Headers, Extra Provider Options, and provider-specific thinking
budgets.

The API key is resolved when LLM Profile runs. The resulting `llm-config` value
contains the resolved key, including when it came from Rivet settings or a
programmatic runtime option. It can therefore appear in execution data,
recordings, previews, or remote transport just like any other node output.

For an intentionally keyless Custom profile, use configured-key mode, clear
both alternative key-name fields, and leave the shared Custom provider key
empty. If a configured programmatic or environment key name is present but
missing at runtime, the profile fails instead of silently retrying without
authentication. An explicit `Authorization` header remains available for
header-authenticated endpoints.

**Extra provider options** in a profile use the same raw request-body contract
as Inline LLM Chat configuration. They must resolve to a JSON object; their
exact top-level names and values are applied after the provider request is
generated and override same-named generated fields. In a fallback chain, each
candidate uses only the Extra provider options stored in that profile.

## LLM profile suspension

Enable **Automatic suspension** when repeated provider outages would otherwise
make every graph run wait for the same slow profile before falling back. Rivet
Studio Server then temporarily suspends the profile after repeated failures or
timeouts. The profile can define:

- **Useful output wait time**: maximum wait for the first usable response
  data from a provider call.
- **Stream inactivity timeout**: maximum pause between useful streamed response
  events after output has started.
- **Failures before suspension**: number of failed or timed-out logical profile
  calls within the failure window before the profile is suspended.
- **Failure window**: rolling period used to count failed or timed-out calls.
- **Suspension duration**: how long the fallback chain skips the profile before
  one recovery attempt is allowed.

Timeouts, transport failures, HTTP 408/429/5xx responses, and slow successful
calls count as failures. Configuration mistakes, authentication errors,
response-schema validation failures, and caller cancellation still fail or fall
back normally but do not count toward suspension. Retries for one profile are
recorded as one logical result, so **Retry on non-200** does not multiply the
failure count.

This behavior is host-activated: standalone Rivet saves these settings but does
not enforce them. Production hosts must supply shared LLM Profile reliability
storage. Rivet Studio Server does this automatically, so all VM processes and
Kubernetes replicas share the same suspension history. Its Project Settings >
**LLM profile suspension** tab shows suspended profiles and profiles awaiting or
running a recovery attempt, and can clear their history.

If every profile in a fallback chain is suspended, LLM Chat fails immediately
instead of trying a profile that is still unavailable. Leave automatic
suspension disabled on the final reliable fallback when the chain must always
make a last attempt.

## Outputs

| Title   | Data Type    | Description                                               |
| ------- | ------------ | --------------------------------------------------------- |
| Profile | `llm-config` | Complete resolved inference profile consumed by LLM Chat. |

## Example

1. Create two LLM Profile nodes with different providers or models.
2. Set one LLM Chat node to **Configuration → From profile**.
3. Use an Array node to collect the profiles in preferred order, then connect
   the resulting `llm-config[]` value to **LLM Profiles**.
4. LLM Chat retries the first profile according to its own **Retry on non-200**
   settings before trying the next profile. Inspect **LLM Attempts** to
   see which profiles and physical attempts ran.
