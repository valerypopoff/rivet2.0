## Overview

LLM Chat is the recommended chat node for new Rivet 2 graphs. It is a vendor-agnostic chat node built on the Vercel AI SDK and supports OpenAI, Anthropic, Google, and custom OpenAI-compatible providers from one node.

Use LLM Chat when you want to:

- switch providers without rewiring the graph
- select one or an ordered fallback chain of reusable [LLM Profile](./llm-profile.mdx) values at runtime
- use OpenAI reasoning models, Anthropic thinking, or Google thinking controls
- provide the API key from settings or from an input port
- call custom OpenAI-compatible Chat Completions or Responses providers by setting `Provider base URL` and `API`
- expose LLM Attempts plus request/response body outputs for provider debugging
- retry non-200 provider responses and inspect one chronological attempt record

The older [Chat Node](./chat.mdx) remains available for existing graphs, but new work should prefer LLM Chat.

## Editor Settings

### Configuration

**Inline** is the backward-compatible default and keeps provider, model, credential,
generation, reasoning, and provider-specific settings in LLM Chat.

**From profile** hides those settings and adds a required **LLM Profiles** input.
Connect one [LLM Profile](./llm-profile.mdx) node to switch the inference
configuration without duplicating or editing the rest of the Chat node, or
connect an ordered `llm-config[]` value for provider/model fallback. Prompt,
response format, Rivet tools, auto-continuation, outputs, request diagnostics,
retry behavior, and cache behavior remain settings of the LLM Chat node.

With a fallback chain, LLM Chat tries profiles from left to right. It performs
all configured **Retry on non-200** attempts for one profile before advancing to
the next. A profile that completes a model round remains active for later
auto-continued tool rounds; only a later failure can advance to another backup.
`LLM Profile Summary` makes recovered failures visible in the ordinary node
output. Enable **Output LLM attempts** to inspect the complete chronological
record, including configuration failures, physical provider retries, and parsed
response validation. Build a
profile array with an [Array](./array.mdx) node when you need more than one
profile. The array is kept intact for each **Run per item** invocation—it does not create one
graph run per profile.

When **Inline** is selected, choose **Export LLM settings to profile node** at the right of the switcher row to
convert the current setup in one step. Rivet creates an LLM Profile node to the
left, copies the provider and inference settings into it, moves any connected
configuration inputs, connects the profile to this LLM Chat, and changes the
Chat node to **From profile**. Prompt, tool, response-format, and downstream
connections stay where they are. You can undo the whole conversion with one
Undo action.

### Model

This section is available in Inline configuration mode.

| Setting                           | Description                                                                                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Provider                          | OpenAI, Anthropic, Google, or Custom provider.                                                                                                                                                               |
| Provider base URL                 | Custom provider only. OpenAI-compatible hosts belong here by choosing Custom provider, not by overriding built-in OpenAI. A full `/chat/completions` or `/responses` endpoint is normalized to its base URL. |
| API                               | Custom provider only. **Completions** is the backward-compatible default and calls `/chat/completions`; **Responses** opts into the OpenAI Responses wire contract at `/responses`.                          |
| Model                             | Provider model. For Custom provider, enter the model ID expected by that provider.                                                                                                                           |
| API key source                    | Use the configured provider key or expose an API Key input port.                                                                                                                                             |
| Alternative programmatic key name | Custom provider only when using a configured key. Programmatic runs can pass this key as a top-level run option. If blank, `customAiApiKey` is used.                                                         |
| Alternative API key env var       | Custom provider only when using a configured key. Defaults to `CUSTOM_PROVIDER_API_KEY`.                                                                                                                     |

### Parameters

Inline LLM Chat supports common generation parameters such as Temperature, Max output tokens, Top P, Top K, presence penalty, frequency penalty, stop sequences, and seed. In From profile mode these settings and their optional input ports belong to LLM Profile. New nodes leave Top P unset unless you fill it in or drive it from an input port. Provider support varies; unsupported settings may be ignored by the provider or model.

### Reasoning

Reasoning settings are provider-specific. They are configured on LLM Chat in
Inline mode and on LLM Profile in From profile mode:

- OpenAI: Reasoning effort and optional reasoning summary.
- Anthropic: Thinking mode, effort, thinking budget, and cache breakpoint TTL.
- Google: Thinking level, thinking budget, and Include thoughts.

**Output reasoning** is always in LLM Chat's **Outputs** section because it
controls whether that Chat exposes the `Reasoning` output.

The node body shows the selected reasoning effort for built-in providers.

### Response Settings

Response format supports Default, Text, JSON object, and JSON schema. JSON object and JSON schema make the Response output emit the parsed structured value instead of a JSON string when parsing succeeds. JSON object falls back to the raw string Response output if the provider response cannot be parsed. JSON schema instead requires the final Response to be an object. In Custom **Completions** mode, JSON object and JSON schema use the Chat Completions `response_format` request field. In Custom **Responses** mode, Rivet uses the Responses API `text.format` contract through the provider adapter. JSON schema adds a Response Schema input port and optional schema name/description settings in either mode.

JSON schema always requires the final value prepared for the **Response** port
to be an object, after Rivet has tried SDK structured output and raw JSON-text
parsing. A string, array, primitive, null, or missing value rejects that LLM
profile. This validation does not use **Retry on non-200** because the provider
request itself succeeded. With an LLM Profile fallback chain, Rivet immediately
tries the next profile. With Inline configuration or no remaining fallback,
the node fails with an error that identifies the final Response type and
explains why non-200 retry was not used.

**Stream response** is also configured here. When enabled, the provider request
uses streaming so Rivet can show live response updates while the node runs.
When disabled, Rivet uses a non-streaming provider request and only displays the
final response. Connected downstream nodes receive only the final response in
both modes. Tool-call rounds can return tool calls before a final structured
response exists; in that case Rivet keeps the tool calls, and auto-continue can
produce the final structured response on a later model round.

### Tools

Tool use enables the Tools input and optional tool-choice controls. Auto-continue mode lets Rivet execute tool calls, send tool results back to the model, and repeat until a normal answer is produced or the maximum tool-round limit is reached. A round is one model response containing one or more eligible tool calls, so a single round can contain multiple parallel calls. After Rivet executes the last permitted round, it makes one final provider request so the model can turn those results into an answer. If that request returns more tool calls, Rivet leaves them unresolved on the normal **Tool Calls** output and does not auto-continue again.

Each [Tool](./gpt-function.mdx) can choose **Result handling**. The default,
**Continue with LLM**, keeps the normal result-and-follow-up loop. **Return
directly** skips the follow-up provider request only when that Tool is the sole
declared Rivet tool call in the current round and its handler succeeds. The
handler's exact string becomes **Response**; its complete function-result message
remains in **All Messages**, while **Messages Sent**, usage, reasoning, request
bodies, and response-token accounting describe only provider calls that actually
occurred. A round with multiple calls always uses normal continuation, including
mixed and all-direct rounds.

**Allow parallel toolcalls** is available for OpenAI, Anthropic, and Custom providers. It permits a supported model to return more than one tool call in a response; it does not require the model to do so. OpenAI and Anthropic receive an explicit provider setting for either switch state. Custom **Responses** mode uses the Responses API `parallel_tool_calls` option for either switch state. Custom **Completions** mode generates `parallel_tool_calls: true` only when enabled and otherwise leaves the field absent so existing endpoints keep their defaults. A same-named field in **Extra provider options** is applied last and therefore overrides the generated value. Some partially compatible Custom endpoints may ignore or reject the field. Google does not show this switch because its current adapter has no equivalent control. In **From profile** mode the switch remains invocation-local and applies only to fallback candidates whose providers support it; unsupported candidates ignore it.

To make tool work visible and configurable in the graph:

1. Enable **Tool use** and **Auto-continue after toolcalls run**.
2. Connect **Tool Calls** directly to the **Tool Call** input of one
   [Delegate Tool Call](./delegate-tool-call.mdx) node.
3. Configure that Delegate to auto-delegate by graph name, call registered
   external functions, or use explicit handler graphs.

That exact existing connection becomes bidirectional automatically for the
duration of auto-continuation. The LLM sends each model tool-call round to the
Delegate, receives its ordered results, and continues generating while both
nodes stay **Running**. There is no extra execution mode, reverse wire, or
waiting state to configure.

LLM Chat shows a nested **round pager** when an invocation has more than one
completed logical model response: for example, **Round 1 · Requested tools**,
**Round 2 · Requested tools**, then **Round 3 · Final answer**. A round is one
completed model response after its provider retries and profile fallback have
resolved; retries, fallback candidates, and individual parallel tool calls do
not create extra LLM pages. A direct-return tool keeps the requesting model
round and adds a terminal **Direct tool result** page. The final LLM page is the
ordinary Response and other graph output that flows downstream. Selecting an
older page is only a display choice: it does not rerun the model, alter ports,
or change downstream execution. Cached, frozen, preloaded, legacy, and
single-result invocations keep the compact one-page output.

While a later model round is streaming, **Current response · Running** remains
the latest page. You can inspect an older completed round and return to the
current response without changing the running graph. If an invocation later
fails, every completed round remains available, but Rivet does not invent a
page for the incomplete round.

Each model tool-call round also appears at the call level on the Delegate. One
model round with several parallel calls is therefore one LLM Chat page but
several selectable Delegate run pages.

**Run per item** LLM Chat nodes are deliberately not upgraded to this connected
continuation behavior. Their Tool Calls wire remains ordinary and each split
invocation uses the internal auto-continuation path, because one shared Delegate
result cannot safely stand for multiple parallel split indexes.

If the model includes normal assistant text in a response that also contains
tool calls, the connected Delegate exposes it on **Message**. That output activates once for every tool call before
the shared batch is dispatched. Its branch and the corresponding tool handler
start in parallel. Normal
tool-result branches start after the Delegate finishes. Put a **Start Async
Branch** node immediately after the message output when that work should overlap
the tools and later LLM rounds; the async trigger returns immediately, while the
root lifecycle still owns all managed async work. In a web app, the final
foreground Chat response can be displayed before that async work finishes.
Consumers still waiting for the final LLM response or another late input remain
in ordinary post-LLM scheduling. If an already-ready pre-tool path itself enters
a cycle, Loop Controller, Race Inputs, or a foreground rejoin, Rivet reports the
unsupported branch before invoking tools. Use **Start Async Branch** as the
explicit boundary for a closed side-effect subtree that should overlap tool
work.

Rivet can converge the pre-tool message and final tool-result branches within the
same round. Consumers that also need the final LLM response or another late
input are deferred; completed continuation branch outputs are promoted after the
owning LLM finishes so the consumer runs once. Outputs from an earlier tool round
are not considered fresh inputs for the current round.

Exactly one eligible connected Delegate is required for this graph-visible
continuation. With none, LLM Chat uses its built-in internal delegation path.
With more than one, Rivet reports an ambiguity error. If auto-continuation stops
because a tool is unknown or **Max tool rounds** is reached, unresolved raw calls
remain available to the ordinary downstream graph path. A single-run Delegate
accepts one raw call; use **Run per item** on the Delegate or select one call
before it when the unresolved output can contain several calls.

### Provider Advanced

Provider Advanced contains optional Headers and Extra provider options. Headers are added to every physical provider request, including retries, fallback candidates, and auto-continued tool rounds. Built-in OpenAI, Anthropic, and Google providers use their provider-owned endpoints. For OpenAI-compatible custom hosts, choose Custom provider, set the Model section's Provider base URL, and select the API contract implemented by that host.

**Extra provider options** must be a JSON object. Rivet adds its fields exactly as written to the top level of the physical provider request after the normal request is generated. Field spelling is preserved, and these values override generated fields with the same name. This intentionally permits low-level control such as `reasoning_effort`, as well as replacement of `model`, `messages`, `input`, `tools`, or response-format fields. Rivet does not validate whether an arbitrary field is supported by the selected provider.

## Custom Provider

Choose Custom provider for OpenAI-compatible APIs such as local model servers or other hosted providers.

For Custom provider, the expected node body order is:

```text
Provider: Custom
Base URL: <url>
Model: <model name>
```

The Base URL line is shown as plain configuration text in the node body, not as a clickable link.

The custom provider API key can come from, in precedence order:

- the API Key input port
- the alternative programmatic key name as a top-level run option, when set
- the alternative API key env var through `pluginEnv` or `process.env`
- the custom-provider key in Settings > LLM

The API Key input port wins when it is enabled. In configured-key mode, `Alternative programmatic key name` lets backend code pass different custom-provider secrets per node as top-level run options, while `Alternative API key env var` lets desktop or Node runs read a named environment variable. If the alternative programmatic key name is blank, Rivet skips the named top-level lookup and still checks the env var name before the shared `customAiApiKey`. The Settings > LLM custom-provider key is the app-side source of that shared key.

A Custom provider URL may be a base URL or a full `/chat/completions` or `/responses` endpoint. Rivet validates an absolute HTTP or HTTPS URL, removes either endpoint suffix and extra trailing slashes, ignores fragments, and preserves query parameters when it builds the selected endpoint. If the adapter and the configured URL provide the same query name, the configured value wins. Changing a query value also invalidates the legacy editor cache without putting the raw value in its cache key.

For an intentionally keyless Custom endpoint, use configured-key mode, clear both alternative key-name fields, and leave the shared Custom provider key empty. If any configured programmatic or environment key name is present but cannot be resolved, Rivet fails that configuration and does not silently retry without authentication. A manually configured `Authorization` header is preserved.

OpenAI, Anthropic, Google, and custom-provider configured keys are set in Settings > LLM. When running through `@valerypopoff/rivet2-node`, unset configured keys can also come from `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, and the canonical custom-provider `CUSTOM_PROVIDER_API_KEY` env var. Legacy `CUSTOM_AI_API_KEY` is still accepted as a compatibility alias.

## Error Handling

LLM Chat normalizes common provider failures into readable errors. For example, an invalid API key should produce a provider request error that includes the HTTP status, provider, model, endpoint, and a hint to check the API key source.

In the Rivet editor, use **Inspect response** beside the normal output controls or
in the full-output toolbar to inspect how the currently selected LLM Chat
invocation ran. The inspector follows the selected graph run and process page,
including live invocations. It reports model attempts, **Provider request
retries**, **LLM profile fallbacks**, tool executions, durations, reported token
usage, and known or unknown cost state in semantic groups. It intentionally
never shows prompts, conversation
messages, generated response text, reasoning text, tool arguments/results,
retrieved documents, credentials, headers, or raw provider bodies. Frozen
outputs, cache replay, and older recordings may show a partial or unavailable
trace when no physical-call metadata exists.

Enable **Output LLM attempts** for one stable, machine-readable chronological record of every configuration, request, retry, and response-validation attempt. `profileIndex` is present for From profile candidates; inline runs omit it. Custom attempts also include `customProviderApi`, so Completions and Responses candidates using the same model name remain distinguishable. LLM Chat itself still fails if every active configuration fails—attempt output is returned only by completed or recovered invocations. Enable **Output request body** to inspect the provider body Rivet sent and **Output response body** to inspect the provider body Rivet received. Both body outputs preserve physical provider-call order, including fallback candidates and auto-continued tool rounds. The response-body diagnostic clones the provider response without changing the stream, and records the complete body; a request that fails before returning an HTTP response has no response-body entry. `LLM Profile Summary` gives an immediately readable succeeded/failed/not-attempted outcome for every configured profile. Request headers and Rivet-managed API key headers are not included in the request body, but prompts and request options in the actual provider body are visible. Rivet disables the Vercel AI SDK's hidden default retries, so the Retry on non-200 switch is the only retry policy for LLM Chat provider requests.
