# Deploy Rivet Studio Server

Rivet Studio Server runs the editor in your browser and lets you manage projects, publish workflow endpoints, and review run recordings on your own host.

## Restore a legacy backup

If a fully uploaded backup fails validation because you edited it, **Proceed
anyway** lets you bypass its original integrity checks. This is dangerous: removed
data will not be restored. Removing recordings, including their whole folder, is
supported this way. You must still confirm replacement after preparation. Unsafe
archives, invalid data, missing required roots and installation/storage safety
checks cannot be bypassed. The original backup is recommended.

On a restore-capable managed PostgreSQL/S3 deployment, open **Settings → Storage →
Restore legacy backup** and select the original `.tar.gz` backup downloaded before
the legacy-to-SQLite upgrade. Review its date and contents, then type
`RESTORE LEGACY BACKUP` to confirm destructive replacement.

Rivet validates the archive before deleting data, pauses application work, imports
and verifies the backup, and restarts automatically. Workflows, published endpoint
paths/history, recordings and supported server settings are restored, including
environment variables entered in the UI and their Browser permissions. Current
database/S3 connections, deployment secrets and administrator access remain
unchanged. If the UI uses OAuth, its shared OAuth settings are also kept; with
key-based UI login, web-app OAuth settings are restored from the backup.
Imported schedules stay disabled. Endpoint URLs use the new host.
Once normal service resumes, restored retention policies apply to historical data
using its original timestamps; restoration does not renew old recordings' age.

This is not a merge and does not back up current destination data. Only registered
application tables and verified referenced artifacts are removed; unrelated objects
and unknown historical versions remain untouched. Runtime-library archives are
retained because another installation could share them; the restored server still
uses only the backup's library catalog. Native modules and executable runtime binaries
cannot be certified from this legacy format and stop validation before deletion.

You can close the browser and reopen the normal Rivet page; during maintenance it
automatically shows restore progress and recovery. The dedicated
`/?restore-legacy-backup` link also works. After deletion starts, errors keep Rivet in maintenance
and offer **Retry restore**; do not manually unblock or clear storage. The installation
must run the restore-capable images and have the required scratch storage and
database/object permissions. No per-restore shell commands are required.
Restore storage must fit the upload, extracted data and runtime-library archive;
an insufficient-space validation message means the dedicated storage needs to be
enlarged before uploading again. Large backups also need adequate container memory.
You can cancel validation or dismiss a non-destructive failure. Once you confirm
replacement, it cannot be cancelled.

## Upload a project bundle

Right-click the workflow library or a destination folder and choose **Upload
bundle**, beside **Upload project**. Select an extracted bundle folder or its ZIP
archive containing `rivet-bundle.json`. Bundle contents must fit within 64 MiB.

Rivet imports the projects and their datasets together into a new folder. Existing
projects are not overwritten. You can then move or rename any imported project;
references within the bundle continue to work. Imported projects are unpublished,
and their Subgraphs use the imported saved-latest drafts. Publish endpoints as
needed afterward. Plugin installations, credentials and server settings are not
included in project bundles.
Disabled nodes, unused library templates and saved variants can retain targets
outside the exported bundle. Supply or select those targets before activating
that configuration; imported internal targets are remapped automatically.

If an old bundle contains several versions of the same project, download it again
with one bundle-wide version choice before uploading. If the upload loses its
connection, refresh the tree before retrying: it may already have completed, and
uploading again creates another folder.

## Installation options

Rivet Server uses PostgreSQL and S3-compatible object storage. Docker Compose or
Kubernetes can deploy the same application; Kubernetes is not required.
The desktop editor and standalone graph runtimes do not require Kubernetes.

On one VM, use local-storage with PostgreSQL and MinIO running in private Docker
containers. For clustered production, use the same application chart
with external PostgreSQL and S3-compatible services. Single-machine installation
does not provide high availability: keep recoverable backups off the VM.

With Docker/Compose running, `yarn studio-server:dev:local-storage`
builds the server, provisions PostgreSQL/MinIO and starts Rivet automatically,
without starting Kubernetes. It adds missing local credentials to private `.env`
once, preserving the existing file; by default use its `RIVET_KEY` to sign in at the printed local address.
The database and object-store containers have private networking and durable
volumes. Do not replace the credential file while keeping those volumes.
Local-storage credentials are shared across tiers:
`RIVET_LOCAL_POSTGRES_PASSWORD`, `RIVET_LOCAL_S3_ACCESS_KEY_ID` and
`RIVET_LOCAL_S3_SECRET_ACCESS_KEY`. Each tier still has separate containers and
data volumes. Older tier-prefixed values are preserved on upgrade when they agree;
conflicting old passwords require explicit configuration, not automatic replacement.

For the six `dev|staging|prod:local-storage|external-storage` commands, configure the same `.env` using
`deploy/studio-server/.env.example`, then use
`yarn studio-server:prod:external-storage -- --manifest <promoted-manifest> --confirm rivet-prod-external`.
External-storage never provisions local substitutes. Production local-storage
has the same promoted-release safety gates. Public TLS/routing and
backups still require deployment configuration.

Default browser ports are dev **8080**, staging **8082**, and production **8083**;
set shared `RIVET_PORT` to override the browser port for any of the six commands.
Tier-specific port variables are no longer used. Two installations cannot use
the same host port simultaneously.
The Docker listener is loopback-only. Stop without deleting data with, for example,
`yarn studio-server:dev:local-storage -- --stop`. Staging/production require their
installation confirmation when stopping as well as starting.

If startup fails after some application services start, Rivet attempts to drain
them while keeping storage available. It does not reset data or automatically
roll back a migrated schema. Follow the supported stack guide to recover the same
installation; do not delete its private deployment state or replace its keys.

All six commands deploy the same Rivet application. Local-storage ignores external
connection settings and uses private PostgreSQL/MinIO; external-storage uses
only the selected tier's external connections. Settings are prefixed by
`RIVET_DEV_`, `RIVET_STAGING_` or `RIVET_PROD_`, except shared local-storage credentials,
browser-port and UI-auth selection. You do not need to edit a storage-mode switch or swap environment files.

Set `RIVET_SERVER_UI_AUTH_MODE=key` (default) or `oauth` in the shared `.env`.
For a fresh installation, start with key mode, configure **Settings → OAuth**
and the administrator-email allowlist in **Settings → Server UI access**, then
select `oauth` and restart. OAuth without complete settings or an allowed email
denies access; it does not fall back to key login. Keep `RIVET_KEY` in either mode
for internal authentication. Development-auth bypass flags are not forwarded.

The [supported stack guide](https://github.com/valerypopoff/rivet2.0/blob/main/developer-docs/studio-server/server-stack.md)
covers Docker startup, optional Kubernetes deployment, private `.env` credentials,
promoted release manifests, installation and upgrades. Release tiers retain schema migration, release identity
and recovery checks. Configure a TLS gateway before exposing the server.

**Settings → Storage** shows PostgreSQL/S3 connections read-only, with secrets
hidden. There is no Local folders option: local-storage uses private PostgreSQL
and MinIO; external-storage uses the services you provide. The panel explains how
to configure the selected tier's connections in `.env` and start its
`external-storage` command. Starting another deployment does not move existing
data—keep the original data and keys until a supported transfer is verified.
The legacy Migration and Local storage upgrade tabs are not shown on managed
deployments. **Restore legacy backup** remains available for original v1 legacy
archives; it is not a general PostgreSQL/S3 backup restore.
Environment variables entered in Rivet's Settings remain supported and are
restored from compatible legacy backups.

### Move an existing installation

Do not replace a running file/SQLite installation with the new images in place.
Export or transfer data with its previous working release first; keep old data
and encryption keys until the new server is verified. The UI restore above
accepts the original version-1 legacy backup, not arbitrary SQLite snapshots.
For other sources use the
[verified migration procedure](https://github.com/valerypopoff/rivet2.0/blob/main/developer-docs/studio-server/vm-to-managed-migration.md).

Old file/SQLite Compose, bare-host and tunnel server launch commands are retired. Existing
running containers are not stopped or deleted by this change.

## Schedule useful work

Open **Scheduled runs** (calendar icon, just above **Settings**) at the bottom of
the project sidebar and choose **+ Add scheduled run** to open its separate editor.
The sidebar shows how many schedules are enabled; paused or completed one-time
schedules are not counted, and no badge is shown when none are enabled.
Give it a name, optionally describe it, select a project and
choose **Saved latest** or **Published**. Rivet runs that version's **Main Graph**:
latest means its saved state at execution time, not unsaved editor changes.
Publishing is not required for Saved latest. Project moves/renames retain the
schedule's project identity; deleting the project or its main graph makes runs fail.
The project picker works like the Subgraph node's **Other projects** picker:
expand folders to browse nested projects, or type a project name or folder path
to find projects even in collapsed folders. Dropdown project rows show their paths;
the selected field shows the project name on one line, with its path on hover.
Select a project with the mouse or arrow keys and Enter. Folder rows only expand
or collapse and cannot become a run target. The details section places Name beside
Project and Description beside Version; these fields stack on narrow screens.
The footer stays visible while the form scrolls: Preview is on the left and the
blue **Save** button on the right. Use the header's close button to discard changes.
**Save** becomes available only after you change the form; reverting all edits
disables it again. Previewing does not count as a change.
Saving or closing returns to the run list; editing an existing schedule also
opens the separate editor.
New schedules start enabled. Use **Pause** or **Unpause** in the scheduled runs
list to control automatic execution; editing a paused schedule does not enable it.
Paused schedules have a darker, dashed-border card and a status pill; enabled
schedules have no status pill. The non-overlap hint appears under Execution.
If an older schedule shows **Unavailable project** despite the project still
existing, edit the schedule and reselect its project before saving.

Choose once, interval, daily, weekly or monthly, with an IANA time zone such as
`Europe/London`. **Preview next runs** shows the calculated times. Intervals use
elapsed minutes from an explicit UTC/offset anchor. Missing daylight-saving times
and monthly dates are skipped; a repeated daylight-saving time runs once. A
one-time date that is ambiguous or nonexistent must be changed.

The optional input must be a JSON object passed to the graph's `input` port.
Leave it blank to preserve Graph Input defaults; `{}` explicitly passes an empty
object. Inputs can contain secrets, so protect your server and its backups. Turn
**Record these runs** on to retain replays; the server's recording setting must
also be enabled. Root and called-project recordings are linked in Run recordings.
Run history remains available even when recording is off or fails.

The server must stay online, but your browser can be closed. Missed runs are
skipped by default; **Catch up latest only** starts only the newest missed run.
Rivet avoids ordinary overlap for a schedule and defaults to one scheduled run
at a time across the server. A run waiting for capacity is skipped after 15 minutes
in the queue, including catch-up runs; downtime before catch-up is queued does
not count toward that limit. Scheduling continues to track due work while other
runs are busy. Rivet supports a **Maximum run duration (minutes)** of 1–1,440
minutes, including preparation.
At that limit, the server cancels the run; it cannot undo external side effects.
Provider credentials, runtime libraries and other server execution settings
still apply. Interactive User Input nodes
cannot wait for a browser and fail in scheduled runs.

Use **Pause**, **Edit**, **Run now** or the trash icon in the card's top right
as needed. **Recent runs** shows the available history count and starts collapsed;
expand it to inspect runs and use the **Open recording** link for a replay.
Choose **10**, **20**, **50** or **100** runs per page and use **Previous** / **Next**
to browse the available history (up to 300 runs).
Active runs appear before completed history, so long-delayed work remains easy
to find and cancel.
Deleting a schedule cancels pending work but does not stop an already-running
graph; use **Cancel run**
for that. A failed/interrupted execution is not retried automatically: external
side effects may already have happened. Inspect it before choosing **Retry run**,
which uses that run's input/settings snapshot and warns about repeated effects.
Even with cancellation, external side effects cannot be undone.
If execution finishes but its outcome cannot be stored, history eventually marks
it interrupted, not failed. Its external work may have succeeded; check side
effects before retrying.

If an action times out or loses its response, retrying the unchanged action in
the same page (including closing/reopening this modal) reuses its request identity
instead of submitting another run. After a full page reload, review the refreshed
schedules/history first. Do not retry an uncertain action more than 24 hours later.
If the action was accepted but the list could not refresh, wait for reconnection;
do not repeat it.

Keep schedules and history in coordinated storage backups. Restoring local data
under a different control identity pauses schedules until reviewed and enabled.
A full clone containing the same control identity is indistinguishable from the
original: keep test clones offline or pause their schedules before starting them.

## Publish a workflow endpoint

Open a saved project in the browser editor, select its **Main Graph**, then open **Project settings → Endpoint**. Choose an endpoint name and click **Publish**. The published route, `/workflows/<name>` by default, runs the saved project version captured by that publish. Saving more changes to the project does not silently update it: use **Update** after reviewing the new draft. The **Published version history** tab lets you inspect or restore an earlier version. **Unpublish** closes the endpoint routes without deleting the saved project.

To delete a project, open **Project settings → Danger zone**. Unpublish its endpoint and all web apps first. Deletion is permanent and also removes its saved datasets, published version history, and run recordings, so download a backup before confirming. Other projects or schedules that use it may stop working.

Danger zone checks which other projects directly reference this project. When connections exist, it shows the
project names and folder paths, whether each connection belongs to a saved draft, published endpoint, or published
web app, and whether it uses this project's **Saved latest**, **Published**, or a legacy project reference.
An incomplete check is clearly marked and can be retried. This is a read-only warning, not a deletion block;
it excludes unsaved edits, archived version history, indirect dependencies, and scheduled runs.

While the project is published, `/workflows-latest/<draft-name>` runs the latest _saved_ draft. The draft name can differ from the published endpoint name until you click **Update**. The settings dialog shows the latest route when there are unpublished changes. It is useful for testing, but it can change whenever the project is saved; use the published route for clients that need a reviewed version. The route prefixes can be changed in **App Settings → Workflow endpoints → Routes**, so use the paths displayed by your server.

For a published endpoint, **Endpoint access** controls where _both_ the published and latest routes can be reached. **External** is the default, including for projects published before this control was added. **Internal network only** removes those routes from the external entry point; callers inside the server network can use the internal addresses shown in Project settings. For example, Docker Compose uses `http://api/internal/workflows/<name>` and `http://api/internal/workflows-latest/<draft-name>`; Kubernetes uses service-specific internal addresses instead. This setting takes effect immediately and does not publish draft changes. “External” describes network reachability, **not** anonymous access: the separate bearer-key requirement is under **App Settings → Workflow endpoints → Access control**. Keep that requirement enabled unless another trusted layer protects the routes.

If someone saves the project after you open Project settings, a Publish, Update, or restore action that would capture executable content is rejected as stale. If someone changes its publication settings, any publication or access action from the older view is rejected. Nothing changes because of a rejected action. Refresh and review the current state, then explicitly try again if you still want the change. This prevents accidentally publishing a colleague's new draft. Moving or renaming a project in the editor keeps its published endpoint name and access policy; changing the endpoint name with **Update** changes its URL.

## Publish a web app

Create a web app in the project, save it, then open **Project settings → Web apps** to publish it independently of the workflow endpoint. Each published app gets `/apps/<slug>` by default, pinned to the saved version captured when you clicked **Publish** or **Update**. When the project has later saved changes and still contains that web app, `/apps-latest/<slug>` serves its latest saved draft. The dialog links to these routes and reports unpublished changes. Unpublishing one app does not delete its design from the project or unpublish the workflow endpoint. See [Rivet Web Apps](./user-guide/rivet-web-apps.md) for building and using one.

If the server uses OAuth for web apps, the **Allowed emails** field controls which signed-in users can open each published app. An empty list denies all signed-in OAuth users. **Save access** applies an access-list change immediately without republishing the app. Web-app publishing and access changes use the same stale-state protection as workflow endpoints: on a conflict, refresh and review before a deliberate retry.
